# Agentic Service Desk — 액터 · 용어 · 경계 · 전제

- 문서 목적: 누가 등장하고, 무엇을 어떤 이름으로 부르며, 어디까지가 우리 책임이고, 무엇을 전제하는가.

## §11 액터  {#s11-actors}

| 액터 | 역할 | 이 시스템과의 관계 |
|---|---|---|
| **최종 이용자** | 모 시스템에서 질문하고, 게재된 답변을 읽고, 후속 질문을 단다 | 이 시스템을 직접 알지 못한다 |
| **모 시스템** | 소스코드와 QnA 이력을 제공하고, 이 시스템이 쓴 답변을 게재받는다 | 지식의 원천이자 **게재 대상**. 양방향 |
| **운영자** | §8.2 의 여덟 대기열을 소화한다 — 티켓·검수·모순·정정·암묵적 해결 확인·승격·지식 공백 | 프론트를 직접 쓰는 유일한 사람이자 **루프의 일부**. 여기서 못 하는 일은 아무도 못 한다 |
| **구축 에이전트** | 소스·QnA 를 읽어 지식 항목을 짓고 갱신·모순 표시 | 로컬 LLM + pi 하네스, 배치 실행 |
| **응답 에이전트** | 질문 트리거로 5단계 파이프라인 수행 | 온라인 경로. **봇 계정**으로 게재한다 |
| **콘텐츠 에이전트** | 주기·임계 트리거로 같은 5단계를 수행해 FAQ·가이드·칼럼·뉴스레터를 만든다 | 배치 경로. 역시 **봇 계정**으로 게재한다 |

> 프론트는 **운영자용 대시보드**다. 이용자는 모 시스템의 QnA 화면에서 게재된 답변을 볼 뿐이다.
## §12 핵심 용어  {#s12-glossary}

| 용어 | 정의 | 혼동 주의 |
|---|---|---|
| **모 시스템 (Parent System)** | 이 서브시스템이 부착되는 운영 중인 서비스 | 지식의 원천이자 게재 대상. 양방향 |
| **QnA 항목** | 질문 하나를 중심으로 답변·후속·상태를 묶은 **대외 관점의 추적 단위** | "이용자에게 이 질문이 어떻게 되었는가"에 답한다. 티켓과 별개이며 상태를 서로 결정하지 않는다 (§6.4) |
| **질문 (Question)** | 최종 이용자가 던진 원문 1건 | QnA 항목의 시작점일 뿐 |
| **후속 (Follow-up)** | 게재된 답변 뒤에 달리는 추가 질문·재질문·이의 | 파이프라인 재실행의 트리거 |
| **답변 초안 (Draft Answer)** | 검수 전, 근거가 붙은 채 대기하는 답변 | 아직 대외 산출물이 아니다 |
| **검수 (Review)** | 초안이 근거에 뒷받침되는지 확인하는 **필수 4단계** | **생성과 분리**해 수행한다 — 입력은 초안과 근거 원문뿐 (§5.5.2). 답변은 국면 종속, 콘텐츠는 전수 사람 승인 |
| **반려 사유 P1~P5** | 추정 채움 · 예외 무시 단정 · 업계 통념 · stale 현재형 · 과잉 일반화 | 다섯 다 문장이 자연스럽고 근거도 붙어 있어 형식 검사로는 안 걸린다 (§5.4.3) |
| **위험 신호** | 2·3국면에서 자동 검수분을 사람에게 올리는 기준 일곱 | 근거 부족·stale·수치 불일치·새 유형 등 (§5.5.4) |
| **게재 (Publish)** | 답변을 모 시스템 QnA 에 올려 이용자에게 노출하는 행위 | 이 시스템이 모 시스템에 가하는 **유일한 쓰기** |
| **봇 계정 (Bot Account)** | 이 시스템이 게재에 쓰는 전용 계정 | **조건부 ingest 배제의 식별 기준**. 내용이 아니라 계정으로 가른다 |
| **명시적 해결** | 사람(이용자·운영자)이 확인해 종결된 상태 | **검증 신호**. 봇 답변에 ingest 자격을 준다 |
| **암묵적 해결** | 사람 확인 없이 해결로 간주된 상태 (타임아웃·자체 판단) | 검증이 아니다. 통계엔 반영하되 **지식 원천으로 쓰지 않는다**. 사람 확인 시 명시적으로 **상향** |
| **등급 상향** | 암묵적 해결이 사람 확인을 받아 명시적 해결이 되는 전이 | 이 시점에 ingest 자격이 발생한다. 강등은 없다 |
| **QnA 기록** | 질문·답변·후속·상태의 시계열 기록 | 지식베이스가 **아니다**. ingest 원재료(Raw) |
| **지식 항목 (Knowledge Entry)** | 1 파일 1 개념. 출처·유효 범위·상태를 가진 인용 가능한 단위 | 소스 원문도 QnA 원문도 아닌 *가공물* |
| **지식베이스 (KB)** | 지식 항목의 집합 = Wiki Layer | |
| **Raw Layer** | 수집된 원본 (코드 스냅샷, 커밋 메시지·PR 설명, QnA 원문) | 질의 대상이 아니라 ingest 입력 |
| **지식 vs 현재 상태** | 변하지 않는 이해 / 지금의 값 | 전자만 ingest 한다. 후자를 굳히면 즉시 stale 이 된다 (§2.2.2) |
| **출처 (Provenance)** | 지식 항목·게재 답변이 유래한 커밋 해시 또는 QnA ID | 1급 시민 |
| **근거 (Grounding)** | 답변이 인용한 지식 항목 식별자 집합 | 신뢰의 최소 단위 |
| **Ingest / Query / Lint** | 원천→지식 생성 / 지식→답변 합성 / 정합성 검사 | llm-wiki 3 연산 차용 |
| **stale** | 출처 커밋이 최신 코드와 어긋나 신뢰할 수 없는 상태 | 삭제가 아니라 **표시**. 게재 답변에도 전파 |
| **모순 (Contradiction)** | 두 지식 항목이 양립 불가능한 주장을 하는 상태 | **양쪽을 남기고 표시**한다 |
| **승격 (Promotion)** | 티켓 해결·반복 QnA 를 지식 항목이나 FAQ 로 올리는 행위 | 루프를 닫는 유일한 연결 고리 |
| **정정 (Correction)** | 게재된 답변이 틀린 것으로 판명되어 고치는 행위 | 경로는 O14 미결 |
| **지식 공백** | 미해결로 종료된 QnA 가 가리키는, 지식베이스가 못 답하는 영역 | 버릴 데이터가 아니라 ingest 우선순위 신호 |
| **모 시스템 어댑터** | 모 시스템과의 모든 입출력을 가두는 한 겹 (소스 리더 · QnA 리더 · 게재 라이터) | 교체 가능성·단일 출구·전제 격리를 담당 (§9.6) |
| **산출물 필터** | 이 시스템이 만든 것을 ingest 입력에서 걸러내는 **단일 집행 지점** | §5.3 규칙이 사는 곳. 우회 경로를 두지 않는다 (§9.7) |
| **온라인 경로 / 배치 경로** | 질문 트리거 답변 산출 / Ingest·콘텐츠·Lint | 같은 로컬 LLM 자원을 놓고 경쟁한다 (§9.5) |
| **작업 대기열 (Queue)** | 운영자의 판단을 기다리는 항목의 묶음. 여덟 종 (§8.2) | 대시보드의 중심. 현황 숫자는 보조다 |
| **방치 비용** | 대기열을 처리하지 않을 때 발생하는 손해 | 대기열 우선순위의 기준. 사고를 내는 대기열과 조용히 정체시키는 대기열은 다르다 |
| **콘텐츠 (Content)** | 질문 없이 주기·조건으로 만들어 내보내는 산출물 (FAQ · 가이드 · 칼럼 · 뉴스레터 등) | 답변과 **같은 5단계 파이프라인**을 쓴다. 트리거만 다르다 |
| **살아있는 문서** | 항상 최신이어야 하는 콘텐츠 (FAQ · 가이드) | stale 되면 **갱신**한다 |
| **해설 / 권고 / 의견** | 칼럼의 세 등급 — 사실의 재구성 / 관찰에서 나온 조언 / 근거 없는 가치 판단 | 해설은 허용, 권고는 **관찰을 함께 밝히는 조건**으로 허용, **의견은 발행하지 않는다** (§7.6) |
| **발행물** | 발행 시점의 스냅샷인 콘텐츠 (칼럼 · 뉴스레터) | 고칠 수 없다. 후속 발행으로만 바로잡는다 |
| **콘텐츠 타입** | 주 입력 · 트리거 · 성격 · 게재처 · 검수 강도 다섯 가지를 선언한 등록 단위 | 확장은 구현이 아니라 **선언 추가**여야 한다 |
| **FAQ** | 반복도가 높고 해결된 QnA 를 승격시켜 만든 공개용 문답 | QnA 분포의 파생물. 승격은 재료 선별, 문서화는 콘텐츠 파이프라인의 일 |
| **티켓 (Ticket)** | 처리 하나의 **작업 기록 단위**. **모든 QnA 가 발행하며**, 자동 처리 건은 발행 즉시 자동 종결된다 | "우리에게 무슨 일이 남았는가"에 답한다. 출처는 QnA·콘텐츠·지식 모순·정정 넷(§6.4.3). **발행 ≠ 대기열 진입** (§6.4.3-1) |
| **답변 이력** | 게재한 답변과 그 **근거·출처·근거 버전**의 기록 | 답변 텍스트는 모 시스템에 있지만 근거는 우리만 안다. stale 전파의 배선 (§6.6) |
| **근거 버전 고정** | 답변 시점의 지식 항목 버전을 함께 기록하는 것 | 링크만 두면 "그때는 맞았다"와 "그때부터 틀렸다"를 구분할 수 없다 (§6.6.2) |
| **판정 (Adjudication)** | 보고 승인·반려·지정하면 끝나는 대기열 항목 | 티켓이 아니다. 상태 기계가 필요 없다 (§6.4.4) |
| **종결 기록** | 티켓을 닫을 때 남기는 **지식 항목의 초안** (일반화된 질문·답·근거·무효화 조건) | 작업 로그가 아니다. 승격을 번역이 아니라 승인으로 만든다 (§6.5) |
| **무효화 조건** | 무엇이 바뀌면 이 지식이 틀려지는가 | **연결형**(코드·설정에 묶음) 또는 **주기형**(재확인 주기). 둘 다 없으면 승격하지 않는다 (§6.5.3) |
| **부분 답변** | 아는 부분만 답하고 모르는 경계를 명시하는 형태 | 침묵과 억지 답변 사이의 기본값 (§5.4.2) |
| **Knowledge Bundle** | 지식베이스를 자기완결적 디렉터리로 담은 배포 단위 (OKF 차용) | 운영 데이터는 포함하지 않는다 |
## §13 시스템 경계  {#s13-boundary}

### 이 시스템이 **소유**하는 것

- 지식베이스 — 지식 항목의 모델과 수명주기 (생성 · 갱신 · stale · 폐기)
- Raw Layer — 소스코드와 **저장소 히스토리**의 보유본, 최신 상태 추적, QnA 이력 수집본
- Ingest / Query / Lint 3 연산과 그것을 수행하는 에이전트 파이프라인
- 모 시스템 어댑터 — 소스 리더 · QnA 리더 · 게재 라이터
- 산출 5단계 파이프라인 (분석 · 조회 · 생성 · 검수 · 게재) — 답변과 콘텐츠 공통
- 콘텐츠 제작 — FAQ · 사용 가이드 · 칼럼 · 뉴스레터의 작성·갱신·발행과 타입 확장 구조
- **QnA 항목의 수명주기와 해결까지의 추적**
- **답변 이력** — 근거 · 출처 · 근거 버전의 기록과 그 기반의 stale 전파 (§6.6)
- 티켓과 그 상태 기계 — 외부 ITSM 에 위임하지 않는다
- **티켓 종결 기록의 형식과 그 초안 생성** (§6.5)
- 게재 답변의 사후 정정 추적
- QnA 기록과 그로부터 나온 통계
- 콘텐츠의 수명주기 — 살아있는 문서의 갱신, 발행물의 회차 누적
- 운영자용 프론트 — **작업 대기열 여덟 종**(§8.2)과 현황 화면 네 종(§8.3)
- 지식베이스의 OKF 번들 내보내기

### 이 시스템이 **소유하지 않는** 것

- 최종 이용자의 계정 · 인증 · 권한 — 모 시스템의 책임이다
- 최종 이용자 대면 UI — 모 시스템이 렌더링한다. 우리는 그 화면에 **답변과 콘텐츠를 올릴 뿐** 화면 자체를 만들지 않는다
- 모 시스템의 도메인 데이터와 비즈니스 로직 — **개인 데이터 조회 질문은 범위 밖**이다 (§2.4)
- 모 시스템의 **설정값 조회** — 지식이 아니라 현재 상태이므로 ingest 하지 않는다 (§2.2.2)
- **모 시스템의 소스코드에 대한 쓰기** — 읽고 추적할 뿐, 고치거나 PR 을 내지 않는다
- 모 시스템에 대한 그 밖의 쓰기 조치 — 허용된 쓰기는 **답변 게재**와 **콘텐츠 게재(문서 면 upsert · 발행 면 create)** 뿐이다 (§7.7)
- **외부 발송 인프라** — 뉴스레터를 메일로 보내지 않는다 (§7.7.3)
- **별도 채널·별도 사이트** — 게재처는 모 시스템 안으로 한정한다 (§7.7.2)
- 외부 ITSM 도구 연동
- LLM 모델 자체의 학습 · fine-tuning
## §14 이 컨셉이 서 있는 전제  {#s14-assumptions}

1. 모 시스템은 하나이며, 소스코드 읽기 접근과 QnA 게시판 **쓰기 접근**이 확보된다
1-1. 모 시스템은 **사내 업무 시스템**이며 이용자는 사내 인증으로 이미 식별된다 (§1.1)
2. 모 시스템의 QnA 는 **게재자 계정을 구분해 보관**한다 — §5.3 규칙이 이것에 의존한다
3. 모 시스템의 QnA 는 **후속 답글이 가능**하다 — §6 추적이 이것에 의존한다
4. 소스코드를 외부 API 로 보내지 않는다 — 그래서 구축 경로는 로컬 LLM 이다
5. 초기 지식베이스는 비어 있다 — 콜드 스타트가 기본 상태이고, 소스코드 ingest 가 첫 채움을 담당한다
6. 티켓을 처리할 사람이 존재한다 (최소 운영자 본인)
7. 콘텐츠를 올릴 자리(FAQ 면·문서 면·발송 경로)가 모 시스템 쪽에 존재하거나 마련된다
8. 실서비스이므로 오답 비용이 실재한다 — 근거 없는 게재보다 "모른다 + 티켓"이 낫다

> 전제 2·3·7 은 **모 시스템에 대한 요구사항**이다. 충족되지 않으면 §5.3 · §6 · §7 을
> 다시 설계해야 하므로, M-002 요구사항 단계에서 가장 먼저 확인할 항목이다.
