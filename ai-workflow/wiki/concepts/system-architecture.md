## §9 시스템 아키텍처 (논리)  {#s9-architecture}

### §9.1 이 절이 정하는 것과 미루는 것  {#s9-1-scope}

아키텍처는 본래 M-003 설계 단계의 산출물이다. 다만 §1~§8 의 결정들이 **논리 구조를
이미 상당 부분 강제**하고 있으므로, 그 강제된 부분만 여기서 확정한다.

| 여기서 정한다 | M-003 으로 미룬다 |
|---|---|
| 컴포넌트와 그 책임 경계 | 언어 · 프레임워크 · 배포 형태 |
| 데이터가 어디에 사는가 (파일 / DB) | 구체적 DB 제품, 스키마 |
| 실행 경로의 분리 (온라인 / 배치) | 검색 구현 (키워드 / 임베딩 / 하이브리드) |
| 규칙이 집행되는 지점 | 로컬 LLM 런타임과 모델 선택 |

코드 규모는 §1.1 에서 확정됐지만 **O9(모델) · O11(지식 입도) · O31(검색 방식)** 이
아직 열려 있다. 이것들을 모른 채 고른 기술은 근거 없는 선택이 된다.

### §9.3 컴포넌트 책임  {#s9-3-responsibilities}

| 컴포넌트 | 책임 | 근거 |
|---|---|---|
| **모 시스템 어댑터** | 모 시스템과의 모든 입출력을 이 한 겹에 가둔다 — **소스와 히스토리** 읽기, QnA 읽기, 게재 쓰기 | 모 시스템은 교체 가능한 외부 의존이다 |
| **Raw 저장** | 수집 원본을 있는 그대로 보관 — 코드 스냅샷과 **커밋 메시지·PR 설명**은 커밋에 고정, QnA 는 **계정과 해결 등급을 함께** | §2, §2.2.1, §5.3 |
| **산출물 필터** | 이 시스템이 만든 것(봇 답변·콘텐츠)을 ingest 입력에서 걸러낸다. 사람 검증분만 통과 | §5.3 |
| **Ingest 오케스트레이터** | 변경 감지 → 재수집 범위 결정 → 구축 에이전트 호출 → 로그 적재 | §4 |
| **구축 에이전트** | 원천을 읽어 지식 항목을 짓고 갱신하며 모순을 표시 | §4 |
| **지식베이스** | 지식 항목의 보관·인덱싱·출처 추적·Lint | §3, §4 |
| **산출 오케스트레이터** | 트리거를 받아 5단계를 실행. 답변과 콘텐츠가 같은 실행기를 쓴다 | §5, §7.1 |
| **운영 도메인** | QnA 항목 상태 기계와 **그와 독립적인 티켓 상태 기계**(§6.4), **답변 이력(근거·버전)**(§6.6), 콘텐츠 타입 레지스트리와 발행 이력, 통계 집계 | §6, §6.4, §6.6, §7.5 |
| **운영자 대시보드** | 대기열 여덟 종과 현황 네 종 | §8 |

### §9.4 저장소가 둘로 갈린다 — 지식은 파일, 운영은 DB  {#s9-4-two-stores}

이 시스템의 데이터는 성격이 전혀 다른 두 무리로 나뉘며, **같은 저장소에 두면 어느
한쪽이 망가진다.**

| | **지식베이스** | **운영 데이터** |
|---|---|---|
| 내용 | 지식 항목 | QnA 항목 상태, 티켓, 발행 이력, 통계 |
| 변경 성격 | 드물게, 묶음으로 (1 ingest = 1 커밋) | 잦게, 건건이 |
| 필요한 것 | 이력 · diff · additive merge · 사람이 읽는 형태 | 조건 질의 · 집계 · 동시성 · 트랜잭션 |
| 적합한 형태 | **파일 + 버전 관리** | **데이터베이스** |

**지식베이스를 파일로 두는 것은 취향이 아니라 §3 차용의 논리적 귀결이다.** llm-wiki 의
운영 모델(1 커밋 = 1 ingest, `log.md` append, additive merge, `[[wikilink]]`)과 OKF 의
번들 형식(디렉터리 = 번들, 1 파일 = 1 개념)은 **둘 다 파일 트리를 전제한다.** 지식을
DB 행으로 넣는 순간 차용한 운영 모델이 성립하지 않고, OKF 번들 내보내기는 별도
변환 작업이 된다.

반대로 QnA 항목 상태나 통계를 파일에 두면 조건 질의와 집계가 불가능해진다.
대시보드의 여덟 대기열은 전부 조건 질의다.

> **귀결**: 두 저장소를 잇는 것은 **출처(provenance)** 다. 운영 데이터의 QnA ID 와
> 지식 항목의 출처 필드가 서로를 가리키며, 이 연결이 stale 전파와 정정 추적의 경로가
> 된다. 출처가 1급 시민이어야 하는 이유가 여기서 구조로 드러난다.

### §9.5 실행 경로가 둘로 갈린다 — 온라인과 배치  {#s9-5-two-paths}

| | **온라인 경로** | **배치 경로** |
|---|---|---|
| 하는 일 | 질문 트리거 답변 산출 | Ingest, 콘텐츠 제작, Lint |
| 우선순위 | 지연 시간 | 정확도 · 처리량 |
| 자원 요구 | 짧고 잦은 추론 | 길고 무거운 추론 |

**둘은 같은 로컬 LLM 자원을 놓고 경쟁한다.** 대규모 ingest 가 도는 동안 질문이 들어오면
답변이 굶는다. 이것은 운영 중 반드시 마주칠 문제이고, 컨셉 단계에서 최소한 **경로가
분리되어 있다는 사실**은 확정해 둔다. 자원 배분 방식은 **O32**.

### §9.6 어댑터가 지키는 것  {#s9-6-adapter}

모 시스템과의 접점을 한 겹에 가두는 이유는 셋이다.

1. **교체 가능성** — 모 시스템의 QnA 구조가 바뀌어도 도메인 로직은 그대로다
2. **단일 출구** — 게재는 되돌릴 수 없는 대외 행위다(§5.2). 출구가 하나여야 감사 기록과 정정 추적이 성립한다
3. **전제의 격리** — §14 의 전제 2·3·7(계정 구분 · 후속 답글 · 게재 자리)은 전부 어댑터가 감당하는 가정이다. 전제가 깨지면 **어댑터만 다시 만들면 된다**

> 전제 1 은 "모 시스템은 하나"다. 어댑터를 두는 목적은 **다중 지원이 아니라 격리**이며,
> 다중 모 시스템은 현재 범위 밖이다.

### §9.7 규칙은 한 곳에서만 집행한다  {#s9-7-single-enforcement}

§5.3 의 되먹임 차단은 **산출물 필터 한 지점에서만** 집행한다. Ingest 를 부르는 경로가
여럿 생기더라도 필터를 우회하는 길은 두지 않는다.

규칙을 여러 곳에 흩어 두면 언젠가 한 곳이 새고, 새는 순간 **오답이 지식이 되어 굳는다.**
이것은 사후에 발견하기 어려운 종류의 고장이다 — 지식베이스는 틀린 채로도 잘 동작하는
것처럼 보이기 때문이다.

### §9.8 연동 계약 — 모 시스템 내부 API  {#s9-8-integration}

수집과 게재 모두 **모 시스템이 제공하는 내부 API**를 통한다 — 이 절이 **O2** 를 닫는다.
DB 직결도 이벤트도 아니다.

| | 얻는 것 | 대가 |
|---|---|---|
| 내부 API | 계약이 **명시적**이라 양쪽을 따로 바꿀 수 있다. 모 시스템의 스키마 변경에 직격탄을 맞지 않는다 | **API 가 주지 않는 것은 읽을 수 없다** |

§9.6 의 어댑터가 곧 이 API 의 클라이언트다. 어댑터 격리를 미리 정해 둔 것이 여기서
값을 한다 — API 가 바뀌어도 도메인 로직은 그대로다.

#### §9.8.1 필요한 API 표면  {#s9-8-1-surface}

앞 절들의 결정이 요구하는 최소 표면이다. **운영자가 곧 모 시스템 개발자이므로**(§8.6),
없는 것은 요청 대상이 아니라 **만들 항목**이다.

| # | 표면 | 방향 | 왜 필요한가 |
|---|---|---|---|
| 1 | 질문 목록 · 상세 | 읽기 | 파이프라인 1단계 입력 |
| 2 | 답변 목록 — **작성자 계정 포함** | 읽기 | **§5.3 되먹임 차단이 이것에 의존한다.** 봇/사람을 계정으로 가른다 (전제 2) |
| 3 | 후속 답글 | 읽기 | §6 지속 추적과 파이프라인 재실행 (전제 3) |
| 4 | **해결 표시 상태** | 읽기 | **§5.3.1 명시적 해결 판정.** ingest 자격이 여기서 나온다 |
| 5 | 답변 게재 | **쓰기** | 파이프라인 5단계. 이 시스템이 모 시스템에 가하는 쓰기 (§13) |
| 6 | 콘텐츠 게재 — **upsert(문서 면) / create(발행 면)** | **쓰기** | §7 콘텐츠. 타입이 넷이어도 자리는 둘이고 연산도 둘이다 (§7.7) |

2 번과 4 번이 특히 중요하다. 이 둘이 없으면 §5.3 의 되먹임 차단 규칙 전체가
집행 불가능해진다 — 규칙은 있는데 판정할 데이터가 없는 상태가 된다.

#### §9.8.2 폴링으로 읽는다 (O19 확정)  {#s9-8-2-polling}

API 이므로 유입 감지는 **폴링**이다. 질문 절대량이 적으므로(§1.3.1) 호출 비용은
문제가 되지 않는다.

> 다만 **폴링 주기가 답변 지연에 그대로 더해진다.** §8.6.3 이 1인 겸업의 검수 지연을
> 이미 걱정하고 있으므로, 여기서 주기를 길게 잡으면 지연이 두 겹이 된다.
> 호출 비용이 낮다는 점을 살려 **분 단위**로 짧게 둔다. 구체 값은 O16 과 함께 정한다.

#### §9.8.3 API 표면이 입력의 상한이다  {#s9-8-3-ceiling}

DB 직결을 택하지 않은 대가는 명확하다 — **API 가 노출하지 않는 것은 이 시스템에
존재하지 않는다.**

그래서 §9.8.1 의 표면 목록은 단순한 연동 명세가 아니라 **이 시스템이 무엇을 알 수
있는지의 경계**다. 표면을 좁히면 기능이 조용히 죽는다. 예를 들어 2 번에서 작성자
계정을 빼면 §5.3 이 무력해지는데, **그 사실이 겉으로 드러나지 않는다** —
파이프라인은 계속 돌고 지식베이스도 계속 자란다. 오답을 섞은 채로.

> **M-002 요구사항 단계의 최우선 확인 항목**은 §9.8.1 의 여섯 표면이다.
> 전제 2·3·7(§14)이 실은 이 목록의 다른 표현이다.
