## §15 미결 쟁점  {#s15-open-questions}

| # | 쟁점 | 왜 컨셉에 영향을 주는가 |
|---|---|---|
| ~~**O1**~~ | ~~모 시스템의 도메인과 규모~~ | **닫힘 (라운드 10)** — 사내 업무 시스템 / 중규모 5만~50만 줄 / 다언어. §1.1 참조. 잔여 확인 항목은 O35 |
| **O2** | 연동 계약의 형태 — 수집(읽기)과 게재(쓰기) 각각 | API / DB 직결 / 이벤트 중 무엇인지 |
| **O3** | 각 등급에 무엇이 들어가는가 — 명시적 해결로 인정할 **구체적 신호**(이용자 버튼 / 운영자 종결 / 그 밖) | 등급 구분 자체는 **확정**(§5.3.1). 남은 것은 편입 기준이며, 모 시스템 QnA 가 어떤 신호를 제공하는지(O2)에 종속된다 |
| **O4** | 승격이 자동인가 사람 승인인가 | 오답 증식 위험 대 운영 부담 |
| **O5** | 티켓 처리 인원과 주체 | 티켓 상태 기계의 복잡도가 결정된다 |
| **O6** | 최종 이용자 식별 방식 | **대폭 축소** — 사내 인증으로 이미 식별된다(§1.1). 남은 것은 QnA 기록의 사내 개인정보 보관 기간·범위뿐 |
| **O7** | 다국어 여부 | 지식 항목 단위와 검색 설계가 달라진다 |
| **O8** | 통계의 소비자와 핵심 지표, **국면별 임계값** | 등급별 분리 집계는 확정(§6.3). 남은 것은 세부 정의와 **국면에 따라 달라지는 임계**(§1.3) — 고정값이면 1국면이 전부 빨간불이 된다 |
| **O9** | 구축 에이전트와 응답 에이전트가 같은 모델인가 | 로컬 LLM 사양·배치 주기·지연 예산 |
| **O10** | 소스코드 보유 형태와 동기화 주기 | Raw Layer 설계와 stale 판정 지연 |
| **O11** | 지식 항목의 입도 (파일 / 모듈 / 기능 단위) | 다언어이므로 **언어 중립 단위**여야 한다(§4). 또한 **고정값이 아니라 국면에 따라 바뀌는 값**일 근거가 있다 — 초기엔 굵게, 코드가 안정된 뒤 세분화 (§1.3.2) |
| **O12** | OKF 번들을 실제로 내보낼 대상이 있는가 | 없다면 형식 준수를 뒤로 미룰 수 있다 |
| ~~**O13**~~ | ~~검수(4단계)의 주체~~ | **닫힘 (라운드 16)** — **국면 종속**: 1국면 전수 사람 검수 → 2국면 위험 신호 선별 → 3국면 표본. 검수는 생성과 분리한다 (§5.5.2~4) |
| **O14** | 게재 후 정정 경로 — 수정 게재 / 철회 / 정정 코멘트 | 모 시스템 QnA 가 무엇을 허용하는지에 종속 |
| **O15** | 봇 계정의 답변자 표기 — 이용자가 "AI 가 쓴 답변"임을 아는가 | §5.3 이 계정 분리를 이미 요구한다. 남은 것은 노출 정책 |
| **O16** | 답변 게재의 지연 예산 (즉시 / 분 단위 / 배치) | 응답 에이전트를 온라인 경로로 둘지 배치로 둘지 |
| ~~**O17**~~ | ~~QnA 항목과 티켓이 하나인가 둘인가~~ | **닫힘 (라운드 12)** — **별개 엔터티(B안)**. 서로 다른 질문에 답하므로 동기화 대상이 아니다 (§6.4) |
| **O18** | 추적의 강제 종료 조건 — 무응답 타임아웃이 있는가, 얼마인가 | 없으면 QnA 항목이 영원히 열려 있어 통계가 왜곡된다. 타임아웃 해결은 §5.3.1 상 **암묵적 해결**이므로 ingest 자격이 없다 |
| **O19** | 후속이 달렸을 때 재실행 트리거 — 즉시 / 폴링 / 이벤트 | O2 연동 형태와 맞물린다 |
| **O20** | **칼럼의 의견·해석을 어디까지 허용하는가** | 지식베이스는 사실을 주지 의견을 주지 않는다. 선을 긋지 않으면 칼럼이 근거 없는 주장의 통로가 된다 (T1) |
| **O21** | 콘텐츠 타입별 **게재처** — 모 시스템 문서 면 / 별도 채널 / 발송 인프라 | 경계의 "허용된 쓰기" 목록이 여기서 확정된다 |
| **O22** | 뉴스레터 구독자 명단을 누가 소유하는가 | **완화** — 사내 구성원 명단이 이미 존재하므로 이 시스템이 소유할 필요가 없다. 남은 것은 발송 대상 범위(전사 / 부서 / 구독 신청) |
| **O23** | 콘텐츠 타입별 발행 주기와 임계 조건 | 배치 스케줄과 로컬 LLM 자원 계획이 여기서 나온다 |
| ~~**O24**~~ | ~~콘텐츠 검수 주체와 강도~~ | **닫힘 (라운드 16)** — **국면 무관 전수 사람 승인.** 살아있는 문서는 diff 검수, 발행물은 전문 검수 + 발행 직전 확인 (§5.5.5) |
| **O25** | 운영자가 몇 명이며 **역할 분리가 있는가** (검수자 / 티켓 처리자 / 승인자) | 1인이면 대기열 여덟 개가 한 사람에게 쏟아진다. 대시보드 구성과 권한 모델이 갈린다 |
| **O26** | 대기열 우선순위를 **시스템이 제시할 것인가**, 운영자가 스스로 고르는가 | 여덟 개를 나란히 두면 위험한 대기열이 묻힌다 (§8.2) |
| **O47** | **위험 신호(§5.5.4)의 임계값** — 유사도·경계선 판정을 어떤 수치로 자르는가 | 2국면 진입 시 필요하다. 너무 느슨하면 사람 검수가 무의미해지고 빡빡하면 전수와 같아진다 |
| **O48** | **국면 전환 판정** — 무엇을 보고 1→2, 2→3 국면으로 넘기는가 | D22·O8 이 모두 국면에 매달려 있는데 전환 시점을 정하는 주체가 없다 |
| **O27** | **누가 지식 항목을 고치는가** — 사람 직접 편집(A) / 사람은 판정만 하고 에이전트가 반영(B) | 출처 추적 체계의 유지 여부가 걸린다 (§8.5) |
| **O28** | 위험 대기열(Q4·Q5)이 쌓일 때 **알림이 있는가**, 어떤 경로인가 | 없으면 대시보드를 열지 않는 날에는 아무도 모른다 |
| **O29** | 운영자 병목을 어디까지 자동화할 것인가 | **부분 답변됨** — 검수에 한해서는 국면 기준으로 올린다(§5.5.3). 남은 것은 승격·모순 판정 등 다른 대기열의 자동화 수준 |
| **O30** | 지식베이스의 버전 관리를 **git 으로 할 것인가** | 파일 저장은 §9.4 에서 확정. 남은 것은 이력 관리 수단이며, llm-wiki 의 "1 커밋 = 1 ingest"를 그대로 쓸지가 걸린다 |
| **O31** | 지식 검색 방식 — 키워드 / 임베딩 / 하이브리드 | O11(입도)에 종속. 코드 규모는 중규모로 확정(§1.1)이므로 자원보다 **검색 품질**이 판단 기준이다 |
| **O32** | 온라인·배치가 로컬 LLM 자원을 어떻게 나눠 쓰는가 | **크게 완화** — 질문 절대량이 적어 충돌 확률이 낮다(§1.3.1). 단순한 우선순위 규칙으로 충분할 가능성이 높다 |
| **O33** | 운영 데이터와 지식베이스의 **일관성 수준** — 출처 링크가 깨졌을 때 어떻게 감지·복구하는가 | 두 저장소를 잇는 것이 출처인데, 그 링크의 무결성을 보장하는 주체가 없다 |
| ~~**O34**~~ | ~~업무 규칙 공백을 어떻게 다루는가~~ | **정리됨 (라운드 13)** — 후보가 셋으로 갈렸다: **히스토리는 원천에 포함**, **설정값은 ingest 하지 않음**, **운영 문서는 티켓 승격**. §2.2~2.3 |
| ~~**O35**~~ | ~~이용자 수와 기존 QnA 이력 축적량~~ | **닫힘 (라운드 11)** — 2,000명 → 7,000명 예정, 가동 1개월로 이력 거의 없음. **진짜 콜드 스타트**이며 국면 구분의 근거가 되었다 (§1.3) |
| **O36** | **W4(채택 실패) 대응** — 메신저 직접 문의 대비 이 시스템을 쓰게 만드는 유인이 있는가 | 질문이 안 들어오면 원천이 마른다. 질문 절대량이 적어 더 취약하다 (§1.2, §1.3.1) |
| **O37** | **FAQ 승격 임계** — 몇 회 반복부터 후보로 볼 것인가 | 이 규모에서 임계가 크면 FAQ 는 영영 만들어지지 않는다. 2~3회도 후보일 근거가 있다 (§1.3.1) |
| **O38** | **기능 도입 순서** — 답변 → FAQ·가이드 → 칼럼·뉴스레터 순으로 켤 것인가 | 콘텐츠는 1국면에 재료가 없다. M-004 구현 순서의 근거 (§1.3) |
| **O39** | **티켓의 구체적 상태 집합** — 열림/진행/완료로 충분한가, 배정·보류·재개가 필요한가 | O5·O25(처리 인원)에 종속. 1인이면 배정이 불필요하다 |
| ~~**O40**~~ | ~~티켓 종결 기록의 구조~~ | **닫힘 (라운드 14)** — **지식 항목의 초안 형식**으로 받는다. 필수 4필드(일반화된 질문·답·근거·**무효화 조건**), 초안은 에이전트가 채우고 사람이 고친다 (§6.5) |
| **O41** | **커밋 위생 확인** — 실제 히스토리에 "왜"가 남아 있는가 | B1 의 값이 여기 달렸다. 표본 확인이 필요하다 (§2.2.1) |
| **O42** | **개인 데이터 조회 질문의 비중** — 크다면 별도 기능으로 재검토할 것인가 | 현재는 범위 밖으로 확정했지만, 비중이 크면 이용자 만족도가 낮게 고착된다 (§2.4) |
| **O43** | **형식적 승인 방지** — 에이전트가 채운 종결 기록 초안을 사람이 읽지 않고 승인하면 §5.3 되먹임 차단이 무력해진다 | 형식만 사람 검증이고 실질은 자기 산출물이 된다 (§6.5.4). O29(자동화 한계)와 같은 뿌리 |
| **O44** | **주기형 무효화 조건의 기본 주기** — 몇 개월로 둘 것인가 | 너무 길면 낡은 지식이 살아 있고, 너무 짧으면 Q5 가 폭주한다 (§6.5.3) |
| **O45** | **답변 이력·티켓의 보존 기간** — 전건 발행이므로 무한정 쌓인다 | 사내 개인정보(질문자 식별)가 붙어 있어 보존 정책이 필요하다. O6 의 잔여와 같은 뿌리 |
| **O46** | **지식 항목의 버전 관리 방식** — 근거 버전 고정이 요구하는 최소 단위는 무엇인가 | O30(git 사용 여부)과 맞물린다. git 이면 커밋 해시가 곧 버전이다 (§6.6.2) |
