## §0 TL;DR — 확정된 것과 열린 것  {#s0-tldr}

### §0.1 이 시스템을 한 줄로  {#s0-1-oneline}

> 사내 업무 시스템(모 시스템)의 **소스코드**와 **QnA 이력**을 지식베이스로 만들고,
> 그 지식으로 **답변과 콘텐츠를 자동 생산·검수·게재**하며, **해결될 때까지 추적**하고,
> 사람 손이 필요한 일은 **티켓**으로 관리하며, 그 전부를 **운영자 대시보드**에 모으는
> 서브시스템.

### §0.2 확정된 결정 55가지  {#s0-2-decided}

| # | 결정 | 절 |
|---|---|---|
| D1 | 본체는 QnA 응답이 아니라 **지식베이스**다. 나머지는 그 위의 표현이다 | §1 |
| D2 | 지식 원천은 **둘** — 소스코드(실행되는 진실)와 QnA 이력(관찰된 현상). 서로를 검증한다 (1국면 제외) | §2 |
| D3 | **출처(provenance)는 1급 시민**이다. 없으면 stale 판정·교차 검증·근거 부착이 성립하지 않는다 | §2 |
| D4 | **llm-wiki 는 운영 모델**, **OKF 는 교환 형식**으로 층을 나눠 차용한다. 코드는 가져오지 않는다 | §3 |
| D5 | 지식베이스는 **에이전트가 짓는다** — pi 계열 최소 하네스 + **로컬 LLM**(소스코드 외부 반출 금지) | §4 |
| D6 | 모든 산출물은 **분석 → 조회 → 생성 → 검수 → 게재** 5단계를 거친다. 실패는 사람의 대기열로 수렴한다 | §5.1 |
| D7 | **시스템이 만든 것은 ingest 하지 않는다.** 단 사람 검증분(명시적 해결·편집 승인)은 해제 | §5.3 |
| D8 | 해결은 **명시적 / 암묵적 두 등급**. ingest 자격은 명시적에만. 등급은 상향만 가능 | §5.3.1~2 |
| D9 | QnA 는 1회 응답이 아니라 **해결까지 추적되는 상태 엔터티**. 후속마다 파이프라인 재실행 | §6 |
| D10 | 답변과 콘텐츠는 **트리거만 다른 같은 것**. 콘텐츠 확장은 구현이 아니라 **타입 선언** | §7.1, §7.5 |
| D11 | 대시보드의 중심은 차트가 아니라 **작업 대기열 8종**. 운영자는 감시자가 아니라 **루프의 일부** | §8 |
| D12 | 저장소는 **지식(파일) / 운영(DB)** 로, 실행 경로는 **온라인 / 배치**로 갈린다 | §9.4~5 |
| D13 | 모 시스템은 **사내 업무 시스템 · 중규모 · 다언어**. 문서에는 **일반화해서만** 기록한다 | §1.1 |
| D14 | 이 시스템은 **국면(콜드 스타트 / 축적 / 성숙)에 따라 다르게 동작**한다. 지표 임계와 기능 도입 순서가 국면에 종속된다 | §1.3 |
| D15 | **QnA 항목과 티켓은 별개 엔터티**다. 서로 다른 질문에 답하므로 동기화 대상이 아니다. 티켓 출처는 넷(QnA·콘텐츠·지식 모순·정정) | §6.4 |
| D16 | 소스 원천은 **코드 + 저장소 히스토리**다. **설정값은 ingest 하지 않고**(지식이 아니라 상태), 운영 문서는 티켓 승격으로 메운다. **개인 데이터 조회는 범위 밖** | §2.2~2.4 |
| D17 | **판단할 수 없는 것은 답하지 않는다.** 아는 만큼 답하고 모르는 경계를 밝힌다 — 침묵과 억지 답변 사이의 **부분 답변 + 경계 명시**가 기본값 | §5.4 |
| D18 | 티켓 종결 기록은 **지식 항목의 초안**이며 **무효화 조건이 필수**다. 초안은 에이전트가 채우고 사람은 고친다 | §6.5 |
| D19 | **모든 QnA 가 티켓을 발행한다.** 티켓은 사람 일감이 아니라 **처리의 기록 단위**이며, 발행과 대기열 진입은 다른 일이다 | §6.4.3-1 |
| D20 | 답변 이력에 **근거·출처·근거 버전**을 함께 기록한다. 링크가 아니라 **버전 고정**이며, 이것이 stale 전파의 배선이다 | §6.6 |
| D21 | **검수는 생성과 분리한다** — 검수의 입력은 초안과 근거 원문뿐. 의도를 알면 "그럴 만했다"로 기운다 | §5.5.2 |
| D22 | **답변 검수 강도는 국면에 따라** 바뀐다 (1국면 전수 사람 → 3국면 표본). 자동화는 시간이 아니라 **기준이 쌓였을 때** 올린다 | §5.5.3 |
| D23 | **콘텐츠는 국면과 무관하게 전수 사람 승인.** 살아있는 문서는 diff 검수, 발행물은 전문 검수 | §5.5.5 |
| D24 | 국면 전환은 **커버리지·정확도·반복성 세 축의 동시 충족**으로 판정한다. **전진은 운영자 승인, 후퇴는 자동** — 완화는 승인받고 강화는 지체하지 않는다 | §1.3.3 |
| D25 | **국면은 되돌아간다.** 새 영역 추가·대규모 코드 변경·이용자 구성 변화가 역행 신호이며, 이용자 3.5배 확장은 **예정된 역행 사건**이다 | §1.3.3 |
| D26 | **형식적 승인은 무검증보다 나쁘다** — 검증 안 한 것에 검증 라벨이 붙기 때문이다. 막는 방법은 감시가 아니라 **강제 입력 지점**(에이전트가 약한 칸을 비워 둔다) | §5.6.1, §5.6.4 |
| D27 | 승인 품질 지표는 **개인 평가가 아니라 시스템 부하의 신호**로 읽는다. 평가로 쓰면 지표만 좋아지고 품질은 그대로다 | §5.6.6 |
| D28 | 칼럼은 **해설·권고만 발행하고 의견은 발행하지 않는다.** 권고는 **관찰을 함께 밝히는 조건**으로 허용한다 — 관찰은 근거다 | §7.6.1~2 |
| D29 | 의견을 금지하는 이유는 근거 원칙만이 아니라 **귀속**이다. 봇이 사내 채널로 낸 의견은 **조직의 입장처럼 읽히고** 책임질 주체가 없다 | §7.6.3 |
| D30 | 운영은 **1인 겸업**이며 **운영자가 곧 모 시스템 개발자**다. 배정·권한 모델·외부 이관·SLA 가 모두 불필요하다 | §8.6 |
| D31 | **D22 완화** — 1국면에도 고신뢰 건은 자동 게재한다. 1인 겸업의 전수 검수는 답변 지연을 낳고 그 지연이 채택 실패로 이어진다 | §8.6.3 |
| D32 | 대기열 정렬은 **방치 비용 × 경과 시간** 2축이며, **시스템이 다음에 볼 것을 제시한다** | §8.6.3 |
| D33 | 티켓 상태는 **자동종결 / 열림 / 진행중 / 보류 / 종결** 다섯. 상태 집합은 조직 규모가 아니라 **작업 리듬**을 따른다 | §6.7 |
| D34 | 연동은 **모 시스템 내부 API**다. 필요한 표면 여섯이 **이 시스템이 무엇을 알 수 있는지의 상한**이며, 표면을 좁히면 기능이 **소리 없이** 죽는다 | §9.8 |
| D35 | 명시적 해결의 신호는 **이용자의 해결 표시**와 **운영자의 확인 종결** 둘이다. 이로써 §5.3 되먹임 차단이 실제로 집행 가능해진다 | §5.3.1-1 |
| D36 | **해결 표시율은 지식 성장의 선행 지표**다. 떨어지면 답변 품질이 그대로여도 몇 주 뒤 성장이 느려진다 | §5.3.1-1 |
| D37 | **사람이 지식 항목을 직접 고친다.** 단 왜 고쳤는지를 남기고, 무효화 조건을 갱신하며, 사람이 고쳤다는 표시를 남긴다 | §8.5.3 |
| D38 | 에이전트는 **사람의 수정을 덮어쓰지 않고 모순으로 올린다**(Q4). llm-wiki 의 additive merge 를 그대로 따른다 | §8.5.4 |
| D39 | **대시보드는 고칠 곳을 지목하고, 편집은 평소 도구로 한다.** 파일 기반 + 개발자 운영이므로 대시보드 내 에디터는 중복 투자다 | §8.5.5 |
| D40 | 승격은 **세 경로**(티켓 해결 · 봇 답변 · FAQ)이고 둘은 이미 사람 손을 거쳤다. **Q7 을 거치는 것은 봇 답변 하나뿐** — 나머지에 승인을 또 붙이면 이중 승인이다 | §6.8.1 |
| D41 | **명시적 해결은 배제를 푸는 자격이지 승격 판정이 아니다.** 이용자의 해결 표시는 "나에게 유효했다"는 증언이지 "일반적으로 옳다"가 아니다 | §6.8.2 |
| D42 | 봇 답변 승격은 **세 조건(코드 연결 · 무반려 통과 · 명시적 해결)** 충족 시 자동. 범위는 국면에 종속되며 1국면에는 자동 승격이 없다 | §6.8.4 |
| D43 | W4 의 실체는 **질문이 기록되지 않는 것**이다. 대응은 인입 경로를 늘리는 것이 아니라 **기록 경로를 만드는 것** | §1.4.1 |
| D44 | **1국면에 QnA 는 메신저를 이길 수 없다.** 경쟁하지 않고 **담당자가 메신저 문의를 티켓으로 기록**해 흡수한다 — 기존 A 경로를 그대로 탄다 | §1.4.2~3 |
| D45 | 유인은 시스템이 아니라 **"같은 질문을 다시 받지 않는 것"**이다. 기록은 봉사가 아니라 자기 시간을 아끼는 투자여야 한다 | §1.4.4 |
| D46 | 콘텐츠 게재처는 **문서 면 · 발행 면 둘**이고 연산도 **upsert · create 둘**이다. 타입이 늘어도 자리는 늘지 않는다 | §7.7 |
| D47 | 게재처는 **모 시스템 안으로 한정**한다. 별도 채널·별도 사이트는 범위 밖이다 | §7.7.2 |
| D48 | **뉴스레터는 발송하지 않고 게시한다.** 도달 하나를 잃고 인프라·개인정보·회수가능성 셋을 얻는다 — T2 완화, T3 소멸 | §7.7.3 |
| D49 | 기능은 **여섯 단계(S0~S5)로 켠다.** 원칙은 **대외 노출은 늦게, 내부 축적은 일찍** — S0~S2 는 아무것도 내보내지 않는다 | §1.5.3 |
| D50 | **가이드는 FAQ 보다 먼저 온다.** FAQ 는 QnA 통계에 종속되지만 가이드는 소스코드만으로 만들 수 있다 | §1.5.1 |
| D51 | 단계 진입 조건에 **운영자의 부하**가 들어간다. 앞 단계 대기열이 밀려 있으면 다음을 켜지 않는다 | §1.5.4 |
| D52 | **지식 항목을 언어별로 나누지 않는다.** 지식베이스는 진실의 저장소이지 표현의 저장소가 아니다 | §2.5.1 |
| D53 | **언어는 산출 시점의 파라미터**다. 1단계에서 질문 언어를 판정하고 3단계에서 그 언어로 쓰되 **근거는 원문 그대로 인용**한다 | §2.5.2 |
| D54 | 지식 항목은 **원천의 언어를 따르고 혼재를 허용**한다. 지식베이스의 1차 독자는 사람이 아니라 **에이전트**이므로 통일보다 **원문 충실성**이 우선이다 | §2.5.3 |
| D55 | 콘텐츠는 **1차 언어로 시작**한다. 두 언어판을 유지하면 살아있는 문서의 "항상 최신"이 두 배로 어려워진다 | §2.5.5 |

### §0.3 이 시스템이 실패하는 방식  {#s0-3-failure-modes}

| 실패 | 어떻게 일어나는가 | 막는 장치 |
|---|---|---|
| **오답이 지식으로 굳는다** | 시스템이 쓴 답변을 시스템이 다시 배운다 | D7 산출물 필터 (§9.7 단일 집행 지점) |
| **차단이 뒷문으로 뚫린다** | 무응답 타임아웃을 해결로 세면 검증 안 된 답이 지식이 된다 | D8 해결 등급 |
| **사고 없이 성장이 멈춘다** | 방치해도 사고가 안 나는 대기열(Q6·Q7·Q8)이 영원히 밀린다 | §8.2 방치 비용 기반 우선순위 |
| **틀린 답이 계속 노출된다** | 코드가 바뀌어 게재물이 낡았는데 아무도 모른다 | 출처 기반 stale 전파 (D3) + Q5 |
| **근거 원칙이 새어 나간다** | 칼럼처럼 의견이 필요한 콘텐츠가 예외가 된다 | 의견 발행 금지 + 칼럼 전용 반려 사유 P6~P8 (§7.6) |
| **AI 가 조직을 대변한다** | 봇이 사내 채널로 낸 권고가 정책 공지로 읽힌다 | P8(정책형 서술) 반려 + 귀속 표시 (§7.6.3, §7.6.5) |
| **질문이 기록되지 않는다** | 메신저로 오가고 사라진다. 담당자는 같은 질문을 계속 받는데 지식은 안 자란다 | 담당자의 티켓 직접 등록으로 흡수 (§1.4). **다만 시스템 안에서 완전히 관측되지 않는다** |
| **정상을 고장으로 오판해 끈다** | 1국면의 낮은 해결률·높은 티켓 비율은 정상인데 대시보드가 빨간불로 표시한다 | 국면별 지표 임계 (§1.3, O8) |
| **성숙했다고 착각한 채 자동화한다** | 국면이 역행했는데 검수 강도는 그대로여서 새 영역의 오답이 그냥 나간다 | 역행 신호 자동 감지 + 후퇴는 자동 (§1.3.3) |
| **검증 라벨만 붙는다** | 대기열이 밀려 초안을 안 읽고 승인하면, 검증 안 된 것이 "사람이 검증함"으로 기록되어 지식이 된다 | 강제 입력 지점 + 불확실성 표시 + 표본 재검증 (§5.6) |
| **지식이 안 자란다** | 티켓을 "완료" 체크로 닫아 승격할 재료가 남지 않는다 | 티켓 종결 시 해결 내용 구조화 (§6.4.5) |
| **낡은 근거가 오답을 그럴듯하게 만든다** | stale 판정이 불가능한 원천(운영 문서)을 들이면 낡은 규정이 근거로 인용된다 | 출처 추적 불가 원천은 ingest 하지 않는다 (§2.2.3) |
| **추정이 근거를 달고 사실이 된다** | 모르는 부분을 그럴듯하게 채우면 붙어 있는 근거가 오답을 검증된 것처럼 보이게 한다 | 억지 답변 금지 + 검수 반려 사유 P1~P5 (§5.4) |
| **승격된 지식이 영영 안 낡는다** | 티켓 파생 지식은 코드에 안 묶여 stale 판정 대상에서 빠진다 | 종결 기록에 **무효화 조건 필수** (§6.5.3) |
| **stale 이 게재물까지 못 간다** | 코드가 바뀌어도 어느 답변이 그 근거를 썼는지 몰라 정정 후보가 안 뜬다 | 답변 이력의 근거·버전 기록 (§6.6.3) |

|---|---|---|

| **운영하며 드러날 것** | O41(커밋 위생) · O42(개인 데이터 질문 비중) · O49(영역별 국면) · O52(칼럼 vs 가이드) · O54(해결 표시율 제고) · O29(자동화 범위) · O12(OKF 번들 수요) | 쓰기 시작해야 알 수 있다 |


> **O41 은 예외적으로 지금 확인할 수 있다** — 모 시스템 저장소의 실제 커밋 히스토리를
> 표본으로 보면 §2.2.1(히스토리 원천)의 값을 판단할 수 있다. 다만 운영자가 곧 커밋을
> 쓰는 사람이므로(§8.6.2) 고정 제약이 아니라 개선 가능한 변수다.

확인할 것은 §9.8.1 의 **API 표면 여섯**이다 — 전제 2·3·7 이 실은 그 목록의 다른
표현이며, 표면이 좁으면 기능이 소리 없이 죽는다(D34).


## §1 시스템 정의와 모 시스템 프로파일  {#s1-definition}

> 모 시스템의 **소스코드**와 **QnA·답변 이력**을 지속 수집해 하나의 지식베이스로
> 구축하고, 그 지식을 근거로 ① **QnA 를 분석해 답변을 자동 작성·검수·게재**하고
> ② **FAQ · 사용 가이드 · 칼럼 · 뉴스레터 같은 콘텐츠를 주기적으로 제작·갱신·게재**하며,
> 게재로 끝내지 않고 **각 QnA 항목을 해결될 때까지 추적**하고, 사람 손이 필요한 것은
> 티켓으로 직접 관리하며, 그 현황을 운영자에게 통계로 보여주는
> **지식베이스 중심 고객지원 서브시스템**.

지식베이스 구축은 부속 기능이 아니라 **본체**이고, 그 위에 **두 개의 산출 축**이 선다 —
질문에 반응하는 **답변**과, 묻지 않아도 먼저 내보내는 **콘텐츠**. 둘은 같은 5단계
파이프라인(§5)을 쓰며 트리거만 다르다.


### §1.1 모 시스템 프로파일  {#s1-1-parent-profile}

> **기록 정책**: 이 저장소는 공개되어 있다. 모 시스템의 **서비스명과 구체적 구조는 쓰지
> 않고**, 설계 판단에 필요한 특성만 일반화해 적는다. 문서에서는 계속 "모 시스템"으로 부른다.

| 항목 | 값 | 설계 함의 |
|---|---|---|
| **유형** | 사내 업무 시스템 | 이용자가 직원이다. 모집단이 작고 고정되어 **반복 질문 비율이 높다** |
| **이용자** | 사내 구성원 — 사내 인증으로 **이미 식별되어 있다** | 익명 처리가 불필요하고 이력 기반 답변이 가능하다 |
| **코드 규모** | 중규모 (5만~50만 줄) | 초기 1회 전체 ingest 는 감당 가능. 이후는 **변경 범위 증분**이 기본 |
| **스택** | 다언어 — Python · TypeScript/JavaScript · 그 외 | 언어별 정적 분석은 비용이 언어 수만큼 배가된다 |
| **이용자 규모** | 현재 약 2,000명 → 약 7,000명 예정 (3.5배) | 질문 절대량이 적다. 자원은 넉넉하고, **통계적 반복 패턴은 얻기 어렵다** |
| **운영 기간** | 본격 가동 1개월 | QnA 이력이 거의 없다 — **진짜 콜드 스타트**다 |
| **코드 변동성** | 서비스 초기라 변경이 잦다 | 지식 항목의 수명이 짧다. stale 이 빠르게 발생한다 |

### §1.2 프로파일이 앞선 결정에 미치는 영향  {#s1-2-implications}

**유리해지는 것**

| 무엇이 | 왜 | 영향 받는 쟁점 |
|---|---|---|
| **콜드 스타트 탈출이 빠르다** | 이용자 모집단이 작고 고정이라 같은 질문이 금세 반복된다. FAQ 승격이 이른 시점에 효과를 낸다 | §6.3 지표 |
| **이용자 식별이 이미 풀려 있다** | 사내 인증이 질문자를 특정한다. 개인정보 부담도 사내 업무 맥락으로 줄어든다 | **O6 대폭 축소** |
| **명시적 해결을 얻기 쉽다** | 질문자와 운영자가 같은 조직이다. "해결됐으면 표시해 달라"를 실제로 요청할 수 있다 | 되먹임 차단의 안전성이 올라간다 (§5.3.1-1) |
| **구독자 명단 문제가 사라진다** | 사내 구성원 명단이 이미 있고, 나아가 뉴스레터를 발송하지 않기로 해 명단 자체가 불필요해졌다 | **T3 · O22 소멸** (§7.7.3) |
| **다언어가 덜 문제된다** | §4 가 정적 분석기가 아니라 **에이전트(LLM)** 로 지식을 짓기로 했기 때문이다. 언어마다 파서를 만들 필요가 없다 | §4 선택의 사후 정당화 |

마지막 항목은 짚어 둘 만하다 — 다언어 코드베이스에서 정적 분석 기반 ingest 를 택했다면
언어 수만큼 도구를 만들어야 했다. **에이전트 기반 선택이 여기서 값을 한다.**

**새로 생기는 위험**

> **W4 — 시스템이 쓰이지 않는 실패**
>
> 사내에서는 담당자에게 메신저로 직접 물으면 된다. 그쪽이 더 빠르면 QnA 게시판에
> 질문이 쌓이지 않고, 그러면 **지식 원천 하나가 말라 루프가 굶는다.**
>
> 이것은 품질 문제가 아니라 **채택 문제**이며, 앞의 W1~W3 과 성격이 다르다.
> 답변을 아무리 잘해도 질문이 안 들어오면 소용이 없다. **질문 유입량 추이**를
> 대시보드 1급 지표로 두어 조기에 감지한다 (§8.3, O8).
>
> 질문 절대량이 적은 규모(§1.3.1)이므로 이 위험은 더 크다 — 몇 건만 줄어도 원천이
> 마르고, 그 변화가 통계적으로 보이기까지 시간이 걸린다. 대응책은 **O36**.


### §1.3 운영 국면 — 이 시스템은 시간에 따라 다른 물건이다  {#s1-3-phases}

이력이 거의 없다는 사실(§1.1)은 단순한 초기 조건이 아니다. **가동 초기에는 §2 의 두
원천 구조가 성립하지 않는다** — QnA 쪽이 비어 있어 교차 검증할 상대가 없다.

| | **1국면 — 콜드 스타트** | **2국면 — 축적** | **3국면 — 성숙** |
|---|---|---|---|
| QnA 이력 | 거의 없음 | 쌓이는 중 | 충분 |
| 유효 지식 원천 | **소스코드뿐** | 둘 다 | 둘 다 + 승격분 |
| 교차 검증(§2) | **성립하지 않음** | 부분 작동 | 작동 |
| 티켓 비율 | **높다 (정상)** | 내려간다 | 낮다 |
| 지식 성장의 주 경로 | **티켓 해결의 승격** | 승격 + ingest | ingest + 갱신 |
| FAQ | 재료 없음 | 후보 등장 | 유효 |
| 콘텐츠(§7) | **가이드는 가능, FAQ 는 불가** (§1.5.1) | FAQ 등장 | 전 타입 |

**국면마다 성공의 모양이 다르다.** 1국면에서 자동 해결률이 낮은 것은 고장이 아니라
정상이다. 이 시기의 티켓은 실패가 아니라 **지식베이스를 채우는 주된 연료**다.
대시보드가 이것을 실패로 표시하면 사람은 멀쩡한 시스템을 끄게 된다.

> **귀결 0 — 국면을 누가 판정하는가**는 §1.3.3 에서 정한다.
>
> **귀결 1 — 지표 임계는 국면에 종속된다.** 해결률·자동 게재 비율의 기대치를
> 고정값으로 두면 1국면에서 전부 빨간불이 된다 (**O8**).
>
> **귀결 2 — 기능 도입 순서가 정해진다.** 다만 콘텐츠를 한 덩어리로 보면 안 된다 —
> FAQ 는 QnA 통계에 종속되지만 **가이드는 소스코드만으로 만들 수 있다.**
> 여섯 단계로 정리한 순서는 §1.5 에 있다.

#### §1.3.1 질문 절대량이 적다는 것의 함의  {#s1-3-1-low-volume}

사내 시스템 2,000명(향후 7,000명) 규모에서 문의는 **일 단위로 소수**다. 이 사실이
양쪽으로 작용한다.

| 완화되는 것 | 악화되는 것 |
|---|---|
| **자원 경합이 사실상 없다** — 온라인 답변 요청이 드물어 배치 ingest 와 부딪힐 일이 적다 (**O32 완화**) | **반복 패턴을 얻기 어렵다** — "N회 반복되면 FAQ" 같은 기준에서 N 이 크면 영영 도달하지 않는다 |
| 로컬 LLM 한 대로 충분하다 | **W4 가 더 위험하다** — 원래 적은 질문이 몇 건만 줄어도 원천이 마른다 |

> **FAQ 승격 임계를 질문량에 맞춰야 한다.** 대규모 서비스의 감각으로 임계를 잡으면
> FAQ 는 만들어지지 않는다. 이 규모에서는 **2~3회 반복도 후보**로 볼 근거가 있다
> (**O37**).

#### §1.3.3 국면 전환은 무엇으로 판정하는가  {#s1-3-3-transition}

국면에 매달린 결정이 셋이다 — 지표 임계(**O8**), 검수 강도(**D22**), 기능 도입
순서(**§1.5**). 그런데 **"지금이 몇 국면인가"를 정하는 주체가 정해져 있지 않았다.**

##### 시간이 아니라 상태로 판정한다  {#s1-3-3-a-state-not-time}

국면은 *가동 몇 개월*이 아니라 **지식베이스가 무엇을 할 수 있는가**로 정의되었다.
따라서 전환 판정도 상태 지표로 한다. **한 지표로는 오판하므로 세 축을 함께 본다.**

| 축 | 무엇을 보는가 | 이것만 보면 생기는 오판 |
|---|---|---|
| **커버리지** | 5단계 중 2단계(조회)에서 **근거를 찾은 비율** | 근거는 찾는데 답이 틀릴 수 있다 |
| **정확도** | 검수 반려율, 명시적 해결률(§6.3) | 정확하지만 답할 수 있는 범위가 좁을 수 있다 |
| **반복성** | 반복 질문 묶음의 등장 — FAQ 재료가 생겼는가 | 질문 공간이 넓어 반복이 안 잡힐 수 있다 |

세 축이 **함께** 올라야 전환이다. 커버리지만 높고 반려율도 높다면 지식은 쌓였으나
부정확한 것이므로 2국면이 아니다.

##### 2국면은 자동 검수를 검증하는 구간이다  {#s1-3-3-b-phase2-role}

2→3 전환에는 축이 하나 더 붙는다. 2국면은 **에이전트 1차 검수 + 위험 신호 선별
사람 검수**로 돌아가므로(§5.5.3), 같은 건에 대한 **자동 판정과 사람 판정의 일치율**을
측정할 수 있다.

> 3국면(에이전트 검수 + 표본)으로 넘어갈 자격은 **그 일치율**이 준다.
> 2국면은 단순한 중간 단계가 아니라 **자동 검수의 신뢰도를 측정하는 구간**이다.

이것이 없으면 3국면 진입은 근거 없는 낙관이 된다.

##### 완화는 승인, 강화는 자동  {#s1-3-3-c-asymmetry}

전환 방향에 따라 주체가 다르다.

| 방향 | 무엇이 일어나는가 | 주체 |
|---|---|---|
| **전진** (1→2→3) | 검수가 느슨해지고 자동화율이 오른다 | **지표가 제안하고 운영자가 승인한다** |
| **후퇴** (3→2→1) | 검수가 빡빡해지고 사람 개입이 는다 | **시스템이 자동으로 내린다** |

시스템이 스스로 "이제 사람 검수를 줄여도 된다"고 결정하는 것은 §5.3 이 배제한
**자기 판단**과 같은 종류다. 반대로 안전한 방향으로 되돌리는 것은 지체할 이유가 없다.

전진 제안은 대기열이 아니라 **현황 화면의 알림**으로 띄운다(§8.3). 운영 전체에서
두어 번 일어나는 일이므로 대기열을 하나 더 만들 일이 아니다.

##### 국면은 되돌아간다  {#s1-3-3-d-regression}

이것이 이 절에서 가장 중요한 부분이다. **국면은 한 방향으로만 가지 않는다.**

| 역행 신호 | 무슨 일이 일어난 것인가 |
|---|---|
| 근거 확보율 급락 | 모 시스템에 **새 영역이 추가**되어 지식이 없는 구역이 생겼다 |
| stale 비율 급등 | **대규모 코드 변경·리팩터링**이 있었다 |
| 신규 유형 질문 비율 급등 | **이용자 구성이 바뀌었다** — 2,000명 → 7,000명 확장(§1.1)이 정확히 이 경우다 |
| 검수 반려율 급등 | 지식이 낡았거나 질문 성격이 달라졌다 |

세 번째가 예정된 사건이라는 점에 유의한다. 이용자가 3.5배로 늘면 새로운 부서·직군의
질문 유형이 유입되고, **성숙했던 시스템이 그 영역에서는 다시 콜드 스타트가 된다.**

> **한계**: 여기서 정한 것은 **전역 국면 하나**다. 그러나 위 사례들은 국면이 실제로는
> *영역별*일 수 있음을 보여준다 — 시스템 전체가 3국면인데 새로 붙은 모듈은 1국면일
> 수 있다. 전역 국면 + 역행 감지로 시작하고, 영역별 국면 관리는 **O49** 로 남긴다.

구체적 임계값은 실데이터 없이 정할 수 없다 — **O8 · O47** 과 함께 실운영에서 정한다.

#### §1.3.2 초기에는 깊게 파지 않는다  {#s1-3-2-shallow-first}

코드 변동성이 높은 시기(§1.1)에 지식 항목을 정교하게 지어 두면 **곧 stale 이 되어
투자가 회수되지 않는다.** 1국면에서는 입도를 굵게 가져가고 자주 갱신하는 편이
합리적이며, 코드가 안정된 뒤 세분화한다 — 입도(**O11**)를 **고정값이 아니라 국면에
따라 바뀌는 값**으로 볼 근거다.
### §1.4 채택 — W4 에 대한 대응  {#s1-4-adoption}

§1.2 는 W4 를 "사내에서는 담당자에게 직접 물으면 되므로 질문이 안 쌓인다"로 적었다.
대응을 정하려면 먼저 **문제를 다시 정의**해야 한다.

#### §1.4.1 이용자가 안 쓰는 것이 아니라 질문이 기록되지 않는 것  {#s1-4-1-reframe}

질문은 어차피 발생한다. 다만 **메신저로 오가고 사라진다.** 그러면 이렇게 된다.

- QnA 이력이 마르고 → 반복 질문 탐지가 안 되고 → FAQ 가 자라지 않는다
- 그런데 담당자는 **같은 질문을 계속 받는다**

> W4 의 실체는 "이용자가 시스템을 외면한다"가 아니라 **"질문이 기록되지 않는다"**이다.
> 그렇게 보면 대응은 **인입 경로를 늘리는 것이 아니라 기록 경로를 만드는 것**이다.

#### §1.4.2 1국면에 QnA 는 메신저를 이길 수 없다  {#s1-4-2-cannot-win}

경로 경쟁을 냉정하게 본다.

| | 메신저 | QnA 게시판 |
|---|---|---|
| 속도 | 즉시 | 폴링 + 검수 지연 (§8.6.3, §9.8.2) |
| 부담 | 한 줄 | 글로 정리해야 한다 |
| 노출 | 1:1 | 공개 — "이런 것도 모르나" 부담 |
| 1국면 답변 품질 | 사람이 답한다 | 지식베이스가 얇다 |

**네 항목 모두 메신저가 유리하다.** 1국면에 이용자를 QnA 로 옮기려는 시도는
실패하기 쉽고, 실패하면 시스템이 쓸모없다는 인상만 남긴다.

#### §1.4.3 경쟁하지 말고 흡수한다  {#s1-4-3-absorb}

> **1국면의 대응**: 이용자를 옮기려 하지 않는다. 대신 **담당자가 메신저로 받은 질문을
> 티켓으로 기록**한다.

운영자 = 담당자 = 개발자(§8.6)이므로 이것이 가능하다. 그리고 **새 메커니즘이 필요 없다** —
기록된 티켓은 §6.8 의 **A 경로(티켓 해결 → 지식)**를 그대로 탄다. 1국면 지식 성장의
주 경로가 원래 A 라는 §1.3 과도 일관된다.

대시보드에 필요한 것은 **질문 직접 등록** 하나다.

| 입력 | 시스템이 하는 일 |
|---|---|
| 질문 원문 + 담당자가 한 답변 | §6.5 종결 기록 **초안을 만든다** |
| — | 사람은 **무효화 조건만 채운다** (§5.6.4 강제 입력 지점) |
| (선택) QnA 에도 게재 | 다른 사람이 검색할 수 있게 된다 — FAQ 의 씨앗 |

마지막이 선택인 이유는 **지식화가 QnA 게재 여부와 무관하게 성립**하기 때문이다.
티켓만 있어도 지식은 자란다.

#### §1.4.4 유인은 시스템이 아니라 담당자 자신의 이익이다  {#s1-4-4-incentive}

기록에는 부담이 따른다. 그 부담을 감수할 이유가 있어야 한다.

> 1인 겸업 담당자에게 가장 강한 유인은 **"같은 질문을 다시 받지 않는 것"**이다.

한 번 기록하면 지식이 되고, 지식이 되면 다음 같은 질문은 자동으로 답해진다.
즉 **기록은 시스템을 위한 봉사가 아니라 자기 시간을 아끼는 투자**다.

이 유인이 성립하려면 **기록 → 지식 → 자동 답변**의 회수 주기가 체감 가능해야 한다.
그래서 §1.4.3 의 등록 부담을 최소로 두는 것이 중요하다 — 부담이 크면 유인이 상쇄된다.

#### §1.4.5 2·3국면에는 경로가 바뀐다  {#s1-4-5-later-phases}

지식이 쌓이면 담당자의 응답이 달라진다.

> 메신저로 물어도 **"그건 여기 있어요"** 하고 링크로 답할 수 있게 된다.

이때부터 이용자가 QnA 를 먼저 보게 되고 경로 경쟁이 비로소 뒤집힌다. 다만 이것은
**결과이지 수단이 아니다** — 1국면에 억지로 유도해서 되는 일이 아니라 지식이 쌓여야
가능해진다.

#### §1.4.6 관측의 한계  {#s1-4-6-blind-spot}

정직하게 적어 둔다. **메신저 문의는 이 시스템에서 보이지 않는다.**

| 관측 가능 | 관측 불가 |
|---|---|
| QnA 유입량 (§1.2 1급 지표) | 메신저로 오간 질문의 양 |
| 운영자의 **수동 등록 건수** | 등록하지 않고 지나간 질문 |

수동 등록 건수가 유일한 간접 지표다. **이 값이 0 에 가까우면 W4 가 진행 중일 수도,
정말 질문이 없을 수도 있다 — 시스템 안에서는 구분되지 않는다.** 이 사각은 지표로
메울 수 없고 운영자의 체감으로만 알 수 있으므로, 대시보드는 그 사실을 숨기지 않는다.

### §1.5 기능 도입 순서  {#s1-5-rollout}

§1.3 은 "답변 → FAQ·가이드 → 칼럼·뉴스레터"를 제안했다. 확정하면서 두 가지를
바로잡는다 — **FAQ 와 가이드는 재료가 다르고**, 순서를 정하는 기준이 재료만이 아니다.

#### §1.5.1 FAQ 와 가이드를 묶은 것이 부정확했다  {#s1-5-1-correction}

| 콘텐츠 | 주 입력 | 1국면에 만들 수 있는가 |
|---|---|---|
| **FAQ** | QnA 통계 (반복 질문 분포) | **아니다** — 통계가 없다 |
| **시스템 사용 가이드** | 지식베이스 (소스코드 파생) | **그렇다** — 소스코드만 있으면 된다 |

**가이드는 QnA 에 종속되지 않는다.** §1.3 표의 "콘텐츠: 1국면 의미 없음"은 정확히는
**FAQ 에 대한 서술**이었다. 가이드는 오히려 일찍 나오는 편이 낫다 — 이용자가 볼 것이
생기고(W4 완화), 지식베이스 품질을 대외적으로 검증받게 된다.

#### §1.5.2 순서를 정하는 기준은 재료만이 아니다  {#s1-5-2-criteria}

기능을 켤 때마다 **대기열이 늘어난다.** 1인 겸업(§8.6)이므로 감당 가능한 총량이
순서를 함께 결정한다.

| 기능 | 새로 생기는 대기열 |
|---|---|
| 수집 · ingest | Q4 모순 · Q8 지식 공백 |
| 수동 등록 · 티켓 | Q1 |
| 답변 초안 | Q2 |
| 답변 게재 | Q5 정정 · Q6 암묵적 해결 확인 |
| 승격 | Q7 |
| 콘텐츠 | Q3 |

> **원칙: 대외 노출은 늦게, 내부 축적은 일찍.**
> 먼저 짓고, 신뢰가 쌓인 뒤 내보낸다.

#### §1.5.3 여섯 단계  {#s1-5-3-stages}

| 단계 | 켜는 것 | 대외 노출 | 다음으로 넘어갈 조건 |
|---|---|---|---|
| **S0** | 수집 + ingest — 지식베이스만 짓는다 | **없음** | 지식 항목이 쌓이고 Lint 가 안정된다 |
| **S1** | 수동 등록 + 티켓 (§1.4.3) | 없음 | 티켓 해결이 지식으로 승격되는 A 경로가 돈다 |
| **S2** | 답변 **초안만** — 게재하지 않는다 | **없음** | 초안 품질이 만족스럽다 (검수 반려율이 낮다) |
| **S3** | 답변 게재 (검수 통과분) | **시작** | 명시적 해결이 쌓이고 커버리지가 오른다 |
| **S4** | 시스템 사용 가이드 | 넓어짐 | QnA 가 쌓여 반복 패턴이 보인다 (2국면 진입, §1.3.3) |
| **S5** | FAQ → 칼럼 · 뉴스레터 | 최대 | — |

**S0~S2 는 아무것도 내보내지 않는다.** 이 구간에서 지식 품질과 답변 품질을 먼저
확인하므로, 오답이 대외로 나갈 위험 없이 시작할 수 있다.

**S2 가 §5.5.3 보다 앞선 단계**라는 점에 유의한다. §5.5.3 은 "1국면에 사람이 검수한다"였고,
S2 는 **검수를 통과해도 게재하지 않는** 단계다. 자동 게재로 가기 전에 신뢰를 쌓는 구간이다.

#### §1.5.4 진입 조건에 부하가 들어간다  {#s1-5-4-load-gate}

각 단계의 넘어갈 조건에는 재료·품질만이 아니라 **운영자가 현재 대기열을 감당하고
있는가**가 함께 들어간다.

> 앞 단계의 대기열이 밀려 있으면 다음 단계를 켜지 않는다.

§5.6.6 이 정의한 부하 신호(승인 소요 시간, 무수정 승인 비율, 반려율 0 수렴)가
여기서 다시 쓰인다 — 그것들이 **다음 기능을 켜도 되는지의 판정 근거**가 된다.

기능을 다 만들어 놓고 순서대로 켜는 것이지, 순서대로 만드는 것이 아니어도 된다.
**도입 순서는 개발 순서가 아니라 활성화 순서**다 — 다만 M-004 에서 무엇을 먼저
만들지 정할 때 이 순서가 자연스러운 기준이 된다.

## §10 핵심 루프  {#s10-core-loop}

```
 ┌────────────── 모 시스템 (Parent System) ──────────────┐
 │  소스코드 저장소       QnA 게시판 (질문·답변·후속)      │
 └──────┬───────────────────────┬───────────────▲────────┘
        │ 변경 추적              │ 수집          │ ⑤게재
        ▼                       ▼               │
 ┌──────────────────  Raw Layer  ───────────────┼────────┐
 │  코드 스냅샷(커밋 고정)   QnA 원문 · 답변 이력 │        │
 │                       (계정 = 봇 / 사람, 해결 등급) │  │
 └──────┬───────────────────────┬───────────────┼────────┘
        │                       │ ※봇답변:해결분만│
        └────▶  Ingest (구축 에이전트)  ◀────────┘        │
                     │  pi 하네스 + 로컬 LLM              │
                     ▼                                    │
 ┌───────────  Wiki Layer = 지식베이스  ────────────────┐  │
 │  1 파일 = 1 지식 항목 · 출처(커밋 / QnA ID) · stale   │  │
 └────┬─────────────────────────────────┬──────────────┘  │
      │ ②조회                           │ Lint            │
      ▼                                 ▼                 │
 ┌─── 산출 파이프라인 (§5) ─────────┐  모순 · stale 검출   │
 │  ①분석  ②지식베이스 조회         │        │            │
 │  ③생성  ④검수 ── 반려 ──┐        │        └─▶ 정정 후보 ┤
 │  ⑤게재 ─────────────────┼────────┼─────────────────────┘
 │                          │        │
 │  ▲ 트리거 둘 (§7.1)      │        │
 │   · 질문 유입 → 답변      │        │
```

루프가 닫히는 지점은 **승격(Promotion)** 이다. 그리고 §5.3 의 봇 답변 배제가 없으면
같은 루프가 오답 증폭기가 된다 — 지식이 자라는 메커니즘과 오답이 자라는 메커니즘은
동일하기 때문이다.
