- 최종 수정일: 2026-08-27

> **개정 이력**
> - v0.1 → v0.2: 무게중심을 "QnA 자동 응답"에서 **지식베이스 구축**으로 이동. 소스코드가
>   지식의 1차 원천으로 추가되고, llm-wiki · OKF 차용과 에이전트 기반 구축이 들어왔다.

>   단방향(수집)에서 **양방향(수집 + 게재)** 으로 바뀌었다.
> - v0.3 → v0.4: 답변 **5단계 규칙**이 확정되고(§5), 되먹임 차단이 "신뢰도 차등"에서
>   **봇 계정 답변의 ingest 배제**라는 단일 규칙으로 확정되었으며(§5.3),
>   QnA 가 1회 응답이 아니라 **해결까지 추적되는 상태 엔터티**가 되었다(§6).
> - v0.4 → v0.5: 봇 답변 배제가 **무조건 배제에서 조건부 배제**로 바뀌었다 — 해결로
>   확정된 봇 답변은 지식에 반영한다(§5.3). 그 결과 되먹임 차단의 강도가 **해결 판정의
>   강도(O3)에 종속**되었다.

## §0 TL;DR — 확정된 것과 열린 것  {#s0-tldr}

### §0.1 이 시스템을 한 줄로  {#s0-1-oneline}

> 모 시스템의 **소스코드**와 **QnA 이력**을 지식베이스로 만들고, 그 지식으로 **답변과
> 콘텐츠를 자동 생산·게재**하며, **해결될 때까지 추적**하고, 그 과정을 **운영자 대시보드**에
> 모으는 서브시스템.

### §0.2 확정된 결정 12가지  {#s0-2-decided}

| # | 결정 | 절 |
|---|---|---|
| D1 | 본체는 QnA 응답이 아니라 **지식베이스**다. 나머지는 그 위의 표현이다 | §1 |
| D2 | 지식 원천은 **둘** — 소스코드(실행되는 진실)와 QnA 이력(관찰된 현상). 서로를 검증한다 | §2 |
| D3 | **출처(provenance)는 1급 시민**이다. 없으면 stale 판정·교차 검증·근거 부착이 성립하지 않는다 | §2 |
| D4 | **llm-wiki 는 운영 모델**, **OKF 는 교환 형식**으로 층을 나눠 차용한다. 코드는 가져오지 않는다 | §3 |
| D5 | 지식베이스는 **에이전트가 짓는다** — pi 계열 최소 하네스 + **로컬 LLM**(소스코드 외부 반출 금지) | §4 |
| D6 | 모든 산출물은 **분석 → 조회 → 생성 → 검수 → 게재** 5단계를 거친다. 실패는 사람의 대기열로 수렴한다 | §5.1 |
| D7 | **시스템이 만든 것은 ingest 하지 않는다.** 단 사람 검증분(명시적 해결·편집 승인)은 해제 | §5.3 |
| D8 | 해결은 **명시적 / 암묵적 두 등급**. ingest 자격은 명시적에만. 등급은 상향만 가능 | §5.3.1~2 |
| D9 | QnA 는 1회 응답이 아니라 **해결까지 추적되는 상태 엔터티**. 후속마다 파이프라인 재실행 | §6 |
| D10 | 답변과 콘텐츠는 **트리거만 다른 같은 것**. 콘텐츠 확장은 구현이 아니라 **타입 선언** | §7.1, §7.5 |
| D11 | 대시보드의 중심은 차트가 아니라 **작업 대기열 8종**. 운영자는 감시자가 아니라 **루프의 일부** | §8 |
| D12 | 저장소는 **지식(파일) / 운영(DB)** 로, 실행 경로는 **온라인 / 배치**로 갈린다 | §9.4~5 |

### §0.3 이 시스템이 실패하는 방식  {#s0-3-failure-modes}

| 실패 | 어떻게 일어나는가 | 막는 장치 |
|---|---|---|
| **오답이 지식으로 굳는다** | 시스템이 쓴 답변을 시스템이 다시 배운다 | D7 산출물 필터 (§9.7 단일 집행 지점) |
| **차단이 뒷문으로 뚫린다** | 무응답 타임아웃을 해결로 세면 검증 안 된 답이 지식이 된다 | D8 해결 등급 |
| **사고 없이 성장이 멈춘다** | 방치해도 사고가 안 나는 대기열(Q6·Q7·Q8)이 영원히 밀린다 | §8.2 방치 비용 기반 우선순위 |

| **근거 원칙이 새어 나간다** | 칼럼처럼 의견이 필요한 콘텐츠가 예외가 된다 | 미해결 — **O20** |

## §1 한 문장 정의  {#s1-definition}

> 모 시스템의 **소스코드**와 **QnA·답변 이력**을 지속 수집해 하나의 지식베이스로
> 구축하고, 그 지식을 근거로 ① **QnA 를 분석해 답변을 자동 작성·검수·게재**하고
> ② **FAQ · 사용 가이드 · 칼럼 · 뉴스레터 같은 콘텐츠를 주기적으로 제작·갱신·게재**하며,
> 게재로 끝내지 않고 **각 QnA 항목을 해결될 때까지 추적**하고, 사람 손이 필요한 것은
> 티켓으로 직접 관리하며, 그 현황을 운영자에게 통계로 보여주는
> **지식베이스 중심 고객지원 서브시스템**.

지식베이스 구축은 부속 기능이 아니라 **본체**이고, 그 위에 **두 개의 산출 축**이 선다 —
질문에 반응하는 **답변**과, 묻지 않아도 먼저 내보내는 **콘텐츠**. 둘은 같은 5단계
파이프라인(§5)을 쓰며 트리거만 다르다.

## §2 지식의 두 원천  {#s2-two-sources}

이 시스템이 다른 QnA 봇과 갈라지는 지점은 지식 원천이 **둘**이고, 그 둘의 성격이
근본적으로 다르다는 것이다.

| | **소스코드** | **QnA·답변 이력** |
|---|---|---|
| 원천의 성격 | 실행되는 진실 (ground truth) | 관찰된 현상 |
| 답하는 질문 | "실제로 어떻게 동작하는가 / 왜 이런가" | "사람들이 실제로 무엇을 묻는가" |
| 정확도 | 그 자체가 동작의 정의 | 과거 답변이 틀렸을 수 있다 |
| 변화 감지 | 커밋 diff | 새 질문 유입 · 표현 변화 |
| 파생 지식 | 기능 · API · 제약 · 에러 원인 · 설정 | FAQ · 사용자 표현 사전 · 질문 빈도 |
| 신선도 관리 | 커밋 추적으로 **자동 stale 판정 가능** | 시간 경과 · 코드 변경에 의해 무효화 |

두 원천은 **교차 검증**된다. 이것이 이 구조의 실익이다.

- QnA 이력의 답변이 맞는지를 **소스코드 지식으로 소급 검증**할 수 있다
- 소스코드가 바뀌면 그에 근거했던 **기존 FAQ·게재 답변이 자동으로 의심 대상**이 된다
- 사용자가 쓰는 표현(QnA)과 코드의 식별자(소스) 사이의 **어휘 격차**를 이 시스템이 메운다

> **핵심 설계 함의**: 모든 지식 항목은 자기가 **어느 커밋 / 어느 QnA 에서 왔는지**를
> 들고 있어야 한다. 출처 추적이 없으면 stale 판정도, 교차 검증도, 근거 부착도
> 불가능하다. 출처는 메타데이터가 아니라 **1급 시민**이다.

## §3 차용하는 외부 컨셉 — llm-wiki 와 OKF  {#s3-borrowed}

둘은 경쟁 개념이 아니라 **층이 다르다**. 겹치지 않게 역할을 나눠 쓴다.

| | **llm-wiki** | **OKF (Open Knowledge Format)** |
|---|---|---|
| 차용하는 층 | **운영 모델** — 지식이 어떻게 들어오고 질의되고 정리되는가 | **교환 형식** — 지식을 어떻게 자기완결적으로 담고 내보내는가 |
| 핵심 구조 | 3-layer: Raw → Wiki → Schema | Knowledge Bundle = 디렉터리 하나 |
| 핵심 연산 | Ingest / Query / Lint | (연산 없음 — 형식 규약만) |
| 단위 | 페이지, `[[wikilink]]` 로 연결 | 1 파일 = 1 개념, 파일 경로 = 개념 ID |
| 메타데이터 | frontmatter + `related_pages` | YAML frontmatter, `type` 필수 |
| 예약 파일 | `index.md`, `log.md` | `index.md`, `log.md` (동일) |
| 방향성 | `PURPOSE.md` (4-element) 가 ingest/query 를 조향 | 없음 |
| 소비자 규약 | 없음 | **MUST NOT reject** — 필드 누락·미지의 타입·깨진 링크에도 소비 실패 금지 |

**우리의 합성**:

- **내부 운영은 llm-wiki 규칙**을 따른다 — Ingest / Query / Lint 3연산, `log.md` append,
  모순 플래그, additive merge, 그리고 stale 검사.
- **외부로 나가는 형식은 OKF 번들**로 담는다 — 지식 항목만이 번들의 내용물이고,
  티켓·QnA 기록 같은 운영 데이터는 포함하지 않는다.
- llm-wiki 의 `PURPOSE.md` 개념은 **모 시스템별 방향성 선언**으로 재사용한다.

> **차용의 원칙**: 개념만 흡수하고 코드는 가져오지 않는다. OKF 는 Apache 2.0 이지만
> 우리 형식은 우리 spec 으로 재정의한다.

## §4 에이전트 기반 지식베이스 구축  {#s4-agent-build}

지식베이스는 사람이 손으로 쓰지 않는다. **에이전트가 짓는다.**

| 항목 | 선택 | 근거 |
|---|---|---|
| 하네스 | **pi 같은 최소 하네스** | "Primitives, not features" — 마크다운 지시문 + 도구 직접 호출 |
| 모델 | **로컬 LLM** | ① 소스코드를 외부로 내보내지 않는다 ② 지속·대량 ingest 비용이 0 에 수렴 ③ 오프라인 재현 가능 |
| 실행 형태 | 배치 ingest + 변경 트리거 | 커밋 유입 시 해당 범위만 재수집 |

**Ingest 절차** (llm-wiki §2 차용):

1. **원천 읽기** — 변경된 소스 범위 또는 신규 QnA 묶음 (**봇 계정 답변은 해결 확정분만** — §5.3)
2. **대상 지식 항목 식별** — 새로 만들 것과 갱신할 것
3. **다중 항목 갱신** — 충돌 시 폐기하지 않고 **양쪽을 남기고 모순 표시**
4. **로그 적재** — `log.md` 에 한 줄, 1 회 ingest = 1 커밋

**Lint** 는 주기적으로 돈다: 모순 미해결 / stale / 고아 항목 / 끊어진 링크 / 참조 부재.
**소스코드 원천이 있으므로 stale 판정이 시간이 아니라 커밋 기준으로 정확해진다** —
이것이 일반 위키 대비 이 시스템의 우위다.

> **역할 분리**: 지식을 *짓는* 에이전트와 답변을 *쓰고 게재하는* 에이전트는 다른 실행
> 경로다. 전자는 배치·정확도 우선, 후자는 온라인·저지연 우선. 같은 모델을 쓸지는 O9.

## §5 산출 파이프라인 — 5단계 규칙  {#s5-pipeline}

### §5.1 확정된 5단계  {#s5-1-five-steps}

이 시스템이 바깥으로 내보내는 모든 산출물 — QnA 답변이든 §7 의 콘텐츠든 — 은
**반드시 이 순서로** 만들어진다. 단계를 건너뛰지 않는 것이 규칙이다.

| # | 단계 | **답변**일 때 | **콘텐츠**일 때 | 공통 산출물 |
|---|---|---|---|---|
| **1** | **분석** | 질문의 의도·유형을 분류하고 기존 QnA 와의 중복·유사도를 판정 | 다룰 주제와 범위를 확정 (QnA 통계 · 발행 이력 · 갱신 대상 참조) | 대상 정의 |
| **2** | **지식베이스 조회** | 질문에 대한 근거 후보 수집 | 주제에 대한 근거 후보 수집 | 근거 후보 집합 |
| **3** | **생성** | 답변 초안 | 문서·기사 초안 (살아있는 문서면 기존본 갱신안) | 초안 + 근거 목록 |
| **4** | **검수** | 초안이 근거에 뒷받침되는지, 근거를 넘어선 주장이 없는지 확인 | 위와 같음. **발행물은 더 엄격하게** (§7.3) | 통과 / 반려 |
| **5** | **게재** | 모 시스템 QnA 에 답변을 올린다 | 타입별 게재처에 발행·갱신한다 | 게재물 + 게재 기록 |

각 단계의 **실패는 사람의 대기열로 수렴한다** — 답변은 티켓(Q1)으로, 콘텐츠는 보류 후
검수 대기열(Q3)로 간다. 어느 쪽도 근거 없이 나가지 않는다.

**이것이 "모른다 + 티켓이 근거 없는 게재보다 낫다"는 원칙의 집행 형태다.**
파이프라인은 답을 만들지 못할 자유가 있고, 그 자유가 없으면 4단계 검수는 형식이 된다.

> **검수(4단계)의 주체가 사람인지 에이전트인지는 아직 미결이다 (O13).** 다만 단계
> 자체는 선택이 아니라 필수로 확정되었다. 이 문서는 "검수 없는 게재는 없다"까지만
> 확정하고, 누가 검수하는지는 다음 라운드로 넘긴다.

### §5.2 자동 게재가 만드는 세 가지 위험  {#s5-2-risks}

게재는 **되돌리기 어려운 대외 행위**다.

| # | 위험 | 내용 | 다루는 방식 |
|---|---|---|---|
| **W1** | **오답의 공개** | 오답이 그대로 이용자에게 노출된다 | 4단계 **검수**를 필수로 세웠다. 검수 주체는 **O13** |
| **W2** | **자기 ingest 되먹임** | 게재한 답변이 다시 ingest 원천이 되어 **오답이 지식베이스에 굳는다** | **조건부 해결** — 봇 답변은 원칙 배제하되 **해결 확정 시 해제** (§5.3). 남은 위험은 해결 판정의 강도에 달렸으므로 **O3** 와 한 몸이다 |
| **W3** | **게재 후 진실 변화** | 소스코드가 바뀌면 이미 게재된 답변이 틀린 것이 된다 | 게재 답변도 출처를 갖고 stale 전파 대상에 포함한다. 정정 경로는 **O14** |

### §5.3 되먹임 차단 규칙 — 시스템 산출물의 조건부 배제  {#s5-3-bot-exclusion}

> **규칙**: 이 시스템이 스스로 만들어 내보낸 것 — 봇 계정 답변과 §7 의 콘텐츠 — 은
> 원칙적으로 Ingest 원천에서 **제외한다.**
> **단, 사람의 검증을 거친 것은 배제를 해제하고 지식에 반영한다.**
> 답변에서는 그 검증이 **명시적 해결**(§5.3.1)이고, 콘텐츠에서는 **사람의 편집·승인**이다.

배제의 근거는 "에이전트가 쓴 것을 에이전트가 다시 배우지 않는다"이고, 해제의 근거는
**해결 확정이 곧 외부 검증 신호**라는 것이다. 답이 실제로 문제를 풀었다면 그것은 더
이상 검증되지 않은 자기 산출물이 아니다.

식별은 계정 단위로 한다 — 내용 판별이나 신뢰도 점수 같은 흐릿한 기준이 아니라,
**"누가 올렸는가"라는 기계적으로 확정 가능한 사실**을 쓴다.

| 용도 | 봇 답변 (추적 중 · 미해결) | 봇 답변 (해결 확정) | 근거 |
|---|---|---|---|
| Ingest — 지식 항목 생성·갱신 | **제외** | **포함** | 해결 확정이 검증을 대신한다 |
| 지식 항목으로의 승격 | **제외** | **포함** | 위와 같음 |
| QnA 기록 보관 | 포함 | 포함 | 추적과 이력에 필요 |
| 해결률·처리량 통계 | 포함 | 포함 | 실제 처리 실적이다 |
| 반복 질문 탐지 · FAQ 승격 후보 | 포함 | 포함 | "무엇이 자주 묻히는가"는 작성자와 무관하다 |

지식으로 삼지 않는 것과 기록하지 않는 것은 다르다. 봇 답변을 통째로 없는 셈 치면
대부분의 QnA 가 통계에서 사라지고 FAQ 는 영영 자라지 않는다.

#### §5.3.1 해결 등급 — 확정 규칙  {#s5-3-1-resolution-grades}

**해결은 하나가 아니라 두 등급이다.** 되먹임 차단의 안전성이 해결 판정의 강도에
달려 있으므로, 등급을 나누는 것이 규칙으로 확정되었다.

| 등급 | 정의 | 검증 신호인가 | **ingest 자격** |
|---|---|---|---|
| **명시적 해결** | 사람이 확인해 종결된 상태 — 이용자의 해결 표시, 운영자·상담원의 확인 종결 | **그렇다** | **부여** |
| **암묵적 해결** | 사람의 확인 없이 해결로 간주된 상태 — 무응답 타임아웃, 에이전트 자체 판단 | 아니다 | **부여하지 않음** |

> **규칙**: 봇 답변의 ingest 배제 해제(§5.3)는 **명시적 해결에만** 적용한다.
> 암묵적 해결은 기록·통계·FAQ 후보에는 반영하되 **지식 원천으로 쓰지 않는다.**

무응답을 검증으로 세지 않는 것이 이 등급 구분의 핵심이다. 만족해서 조용한 것과
포기하고 떠난 것은 데이터상 같은 모양이며, 둘을 구분하지 못하는 신호에 지식의
자격을 줄 수는 없다.

#### §5.3.2 등급은 올라갈 수 있다  {#s5-3-2-promotion}

등급은 고정이 아니다. **암묵적 해결로 닫힌 항목이 나중에 사람 확인을 받으면 명시적
해결로 상향**되고, 그 시점에 ingest 자격이 발생한다. 반대 방향(명시 → 암묵)의 강등은
없다 — 한 번 사람이 확인한 사실은 시간이 지나도 확인된 사실이다.

이 상향 경로 덕분에 암묵적 해결은 **버려지는 것이 아니라 대기하는 것**이 된다.
운영자가 대시보드에서 암묵적 해결 건을 확인해 주는 행위가 곧 지식베이스를 키우는
작업이 되며, 이는 §6.3 의 지표와 맞물려 운영자가 무엇을 먼저 봐야 하는지를 알려준다.

## §6 QnA 수명주기 — 게재는 끝이 아니다  {#s6-lifecycle}

**QnA 항목은 답변 1회로 종료되지 않는다.** 해결로 처리될 때까지 추적되는 **상태를 가진
엔터티**다. 이것이 이 시스템을 "질문 하나에 답 하나"를 반환하는 봇과 구분한다.

### §6.1 상태  {#s6-1-states}

| 상태 | 의미 | 다음으로 |
|---|---|---|
| **접수** | 질문이 들어와 추적이 시작됨 | 파이프라인 실행 |
| **답변 게재됨** | 5단계를 통과해 답변이 올라감 | 해결 / 후속 발생 / 무응답 |
| **후속 진행** | 추가 질문·재질문·이의가 달림 | 파이프라인 **재실행** |
| **사람 대기** | 티켓으로 넘어가 사람 손을 기다림 | 사람이 해결 |
| **해결(명시적)** | 사람이 확인해 종결됨 | 승격 판단. **봇 답변도 ingest 자격을 얻는다** |
| **해결(암묵적)** | 사람 확인 없이 해결로 간주됨 (타임아웃 등) | 통계·FAQ 후보에만 반영. 사람 확인 시 **명시적으로 상향** |
| **종료(미해결)** | 해결되지 못한 채 닫힘 | 지식 공백으로 기록 |

### §6.2 추적이 만드는 두 가지 성질  {#s6-2-properties}

- **파이프라인은 반복 실행된다.** §5 의 5단계는 QnA 항목당 1회가 아니라, 후속이 달릴
  때마다 다시 돈다. 재실행 시 이전 답변과 후속 질문이 1단계의 입력에 포함된다.
- **해결 판정이 종료 조건이자 모든 통계의 분모다.** 무엇을 해결로 볼지가 정해지지
  않으면 추적은 끝나지 않고, 해결률도 계산되지 않는다 (**O3**).

> **미해결로 종료된 QnA 는 버려지는 데이터가 아니라 지식 공백의 신호다.** 지식베이스가
> 답하지 못한 영역을 가리키므로, ingest 우선순위와 소스코드 보강 지점을 알려준다.

### §6.3 해결 등급이 지표를 가른다  {#s6-3-metrics}

해결률을 하나의 숫자로 뭉치면 실제 품질이 가려진다. **등급별로 분리 집계한다.**

| 지표 | 의미 | 읽는 법 |
|---|---|---|
| **명시적 해결률** | 사람이 확인해 닫힌 비율 | **진짜 품질 지표.** 이것이 올라가야 시스템이 나아진 것이다 |
| **암묵적 해결 비율** | 확인 없이 닫힌 비율 | **경고 지표.** 높거나 오르고 있으면 이용자가 확인해 주지 않고 그냥 떠난다는 뜻일 수 있다 |
| **미해결 종료율** | 끝내 닫히지 못한 비율 | 지식 공백의 크기 |

암묵적 해결 비율은 특히 조심해서 읽어야 한다 — 이 숫자는 "잘 해결됐는데 굳이 표시를
안 한 것"과 "포기하고 떠난 것"을 함께 담고 있다. 그래서 **단독으로는 좋고 나쁨을
말할 수 없고, 명시적 해결률과 함께 읽어야 한다.** 둘이 같이 오르면 유입이 는 것이고,
암묵만 오르면 품질이 의심되는 상황이다.

이 구분이 프론트 화면의 뼈대가 된다. 세부 지표 정의는 **O8**.

### §6.4 짚어야 할 모호함 — QnA 항목과 티켓의 관계  {#s6-4-ambiguity}

QnA 항목이 상태를 갖고 해결까지 추적된다면, 그것은 이미 **티켓의 성질**(상태 기계,
종결 조건, 담당)을 가진다. 그렇다면 둘은 같은 것인가 다른 것인가.

| 후보 | 구조 | 장점 | 대가 |
|---|---|---|---|
| **A. 하나의 엔터티** | QnA 항목이 추적 단위이고, "티켓"은 사람 개입이 필요한 상태를 가리키는 이름 | 이중 관리 없음, 추적 끊김 없음 | 대외(QnA)와 내부(운영) 관심사가 한 곳에 섞인다 |
| **B. 두 엔터티** | QnA 항목과 티켓이 별개이고, 필요 시 티켓을 생성해 연결 (1:N 가능) | 대외/내부 분리, 티켓에 운영 필드를 자유롭게 | 두 상태를 동기화해야 하고 어긋날 수 있다 |

**O17** 로 올린다. 데이터 모델 전체가 여기서 갈리므로 컨셉 단계에서 닫는 것이 맞다.

## §7 콘텐츠 제작 — 능동 산출물  {#s7-content}

지식베이스는 질문에 답하기 위해서만 쓰이지 않는다. **묻지 않아도 먼저 내보내는
산출물**이 있고, 이것을 콘텐츠라 부른다.

### §7.1 답변과 콘텐츠는 트리거만 다르다  {#s7-1-unified}

| | **QnA 답변** | **콘텐츠** |
|---|---|---|
| 트리거 | 질문 유입 (수동적) | 주기 또는 조건 도달 (능동적) |
| 대상 | 질문자 1인 | 불특정 다수 |
| 입력 | 질문 + 지식베이스 | QnA 통계 + 지식베이스 |
| 파이프라인 | §5 의 5단계 | **§5 의 5단계 (동일)** |

**둘은 같은 파이프라인을 쓴다.** 분석 → 지식베이스 조회 → 생성 → 검수 → 게재는
답변 전용 절차가 아니라 이 시스템이 무언가를 바깥으로 내보낼 때 거치는 **공통 절차**다.
답변은 "질문이 트리거인 콘텐츠"의 특수한 경우로 볼 수 있다.

이렇게 보면 "그 외 콘텐츠를 추가 가능하게"라는 요구가 자연히 풀린다 — 새 콘텐츠를
추가하는 일이 **새 파이프라인을 만드는 것이 아니라 타입을 등록하는 것**이 되기 때문이다.

### §7.2 콘텐츠 타입  {#s7-2-types}

| 타입 | 주 입력 | 트리거 | 성격 | 게재처 |
|---|---|---|---|---|
| **FAQ** | QnA 통계 (반복 질문 분포) | 주기 + 임계 도달 | 살아있는 문서 | 모 시스템 FAQ 면 |
| **시스템 사용 가이드** | 지식베이스 (소스코드 파생 지식 중심) | 주기 + 코드 변경 | 살아있는 문서 | 모 시스템 문서 면 |
| **칼럼** | 지식베이스 + QnA 통계 | 주기 | 발행물 | 모 시스템 또는 별도 채널 |
| **뉴스레터** | 기간 내 변경·발행 요약 | 주기 | 발행물 | 구독자 발송 |
| *(확장)* | 타입마다 선언 | 타입마다 선언 | 둘 중 하나 | 타입마다 선언 |

FAQ 가 여기 있는 것에 유의한다 — FAQ 는 §6 의 QnA 승격에서 후보가 나오지만,
**실제 문서로 쓰이고 갱신되는 것은 콘텐츠 파이프라인의 일**이다. 승격은 재료를
고르는 단계이고, 콘텐츠 제작은 그 재료로 문서를 만드는 단계다.

### §7.3 살아있는 문서 vs 발행물  {#s7-3-living-vs-issued}

콘텐츠 타입을 가르는 **가장 중요한 축**이다. 이 구분이 없으면 "이미 발송한 뉴스레터를
갱신한다" 같은 성립하지 않는 요구가 생긴다.

| | **살아있는 문서** (FAQ · 가이드) | **발행물** (칼럼 · 뉴스레터) |
|---|---|---|
| 정체성 | 항상 최신이어야 한다 | 발행 시점의 스냅샷이다 |
| 버전 | 최신 1개가 유효 | 시계열로 누적 |
| 근거가 stale 되면 | **갱신한다** | 고칠 수 없다 — 후속 발행으로 바로잡는다 |
| 재실행의 의미 | 같은 문서를 다시 씀 | 새 회차를 씀 |
| 실패의 비용 | 낮다 (고치면 된다) | **높다 (회수 불가)** |

> **함의**: 발행물은 §5.2 의 W3(게재 후 진실 변화)를 **해소할 수 없다.** 살아있는
> 문서는 갱신으로 W3 를 흡수하지만, 이미 나간 뉴스레터는 되돌릴 수 없다.
> 그래서 **발행물의 검수는 살아있는 문서보다 엄격해야 한다** (O24).

### §7.4 콘텐츠 특유의 긴장  {#s7-4-tensions}

| # | 긴장 | 내용 |
|---|---|---|
| **T1** | **칼럼과 근거 원칙의 충돌** | 이 시스템의 원칙은 "근거 없으면 내보내지 않는다"인데, 칼럼은 본질적으로 **해석과 의견**을 담는다. 지식베이스는 사실을 주지 의견을 주지 않는다. 어디까지 허용할지 정하지 않으면 칼럼은 근거 없는 주장의 통로가 된다 (**O20**) |
| **T2** | **회수 불가능한 발송** | 뉴스레터 발송은 게재보다 되돌리기 어렵다. 정정문을 보낼 수는 있어도 이미 읽힌 것은 되돌아오지 않는다 |
| **T3** | **구독자 명단의 소유** | 뉴스레터에는 수신자 명단이 필요하다. 그런데 §13 경계는 "최종 이용자의 계정·개인정보는 모 시스템의 것"이라고 선언했다. 이 둘은 충돌한다 (**O22**) |
| **T4** | **자기 참조** | 콘텐츠도 이 시스템이 쓴 것이므로 ingest 되먹임 대상이다. FAQ 를 ingest 하면 지식베이스가 자기 요약을 다시 배우는 순환이 된다 — §5.3 규칙이 콘텐츠에도 그대로 적용되는 이유 |

### §7.5 확장 규칙 — 타입 등록  {#s7-5-extension}

새 콘텐츠 타입을 추가하는 것은 코드를 새로 짜는 일이 아니라 **선언을 추가하는 일**이어야
한다. 타입이 선언해야 하는 것은 다음 다섯 가지다.

1. **주 입력** — QnA 통계 / 지식베이스 / 둘 다 중 무엇을 읽는가
2. **트리거** — 주기인가, 임계 도달인가, 둘 다인가
3. **성격** — 살아있는 문서인가 발행물인가 (§7.3)
4. **게재처** — 어디에 내보내는가
5. **검수 강도** — 누가 어느 수준으로 검수하는가

이 다섯 가지만 선언하면 §5 의 5단계 파이프라인이 그대로 돌아간다. 이것이 확장
가능성의 실체이며, 그렇지 않으면 콘텐츠 타입마다 별도 구현이 쌓여 유지가 불가능해진다.

## §8 운영자 대시보드  {#s8-dashboard}

### §8.1 조회 화면이 아니라 작업대다  {#s8-1-workbench}

대시보드는 이 시스템에 사람이 접근하는 **유일한 창구**다. 최종 이용자는 모 시스템
화면만 보고, 운영자만 이 프론트를 쓴다. 그래서 여기서 할 수 없는 일은 **아무도 할 수
없는 일**이 된다.

앞 절들을 쌓아 오는 동안 **운영자가 판단을 내려야 하는 지점이 여덟 군데** 생겼다.
현황 숫자를 보여주는 화면으로 설계하면 그 여덟 개가 갈 곳을 잃는다.

> **설계 원칙**: 대시보드의 중심은 차트가 아니라 **작업 대기열**이다.
> 현황 숫자는 대기열이 왜 쌓였는지를 설명하는 보조 정보다.

### §8.2 작업 대기열 — 운영자가 결정하는 여덟 지점  {#s8-2-queues}

| # | 대기열 | 무엇이 쌓이는가 | 운영자의 행위 | 방치 비용 | 근거 |
|---|---|---|---|---|---|
| **Q1** | **티켓** | 파이프라인의 모든 실패 경로 | 조사·해결·종결 | **높음** — 이용자가 기다리고 있다 | §5.1 |
| **Q2** | **검수 대기 (답변)** | 게재 전 답변 초안 | 승인 / 반려 | **높음** — 답변이 나가지 못한다 | §5.1-4, O13 |
| **Q3** | **검수 대기 (콘텐츠)** | 발행 전 콘텐츠, 특히 발행물 | 승인 / 반려 / 수정 | 중간 — 발행이 밀린다 | §7.3, O24 |
| **Q4** | **모순** | Lint 가 찾은 양립 불가 지식 항목 쌍 | 어느 쪽이 옳은지 판정 | **높음** — 모순된 지식이 계속 답변에 쓰인다 | §4 |
| **Q5** | **정정 후보** | 근거가 stale 된 게재 답변·살아있는 문서 | 정정 / 갱신 / 무시 | **높음** — 틀린 내용이 계속 노출된다 | §5.2 W3 |
| **Q6** | **암묵적 해결 확인** | 사람 확인 없이 닫힌 QnA | 확인해 **명시적으로 상향** | 낮음 — 다만 **지식이 자라지 않는다** | §5.3.2 |
| **Q7** | **승격 후보** | 티켓 해결 내용, 반복 질문 묶음 | 지식 항목 / FAQ 로 승격 | 낮음 — 기회 손실 | §10 루프, O4 |
| **Q8** | **지식 공백** | 미해결로 종료된 QnA 가 가리키는 영역 | ingest 우선순위 지정 | 낮음 — 같은 질문이 계속 실패한다 | §6.2 |

**방치 비용이 우선순위다.** 여덟 개를 나란히 늘어놓으면 운영자는 무엇부터 볼지 모른다.
Q4·Q5 는 **틀린 내용이 지금 이 순간 노출되고 있다**는 뜻이므로 Q6·Q7·Q8 보다 앞선다.
Q1·Q2 는 사람이 기다리고 있다는 점에서 시간에 민감하다.

> **주의**: Q6·Q7·Q8 은 방치해도 사고가 나지 않는다. 그래서 **영원히 밀린다.**
> 이 셋이 밀리면 시스템은 조용히 성장을 멈춘다 — 사고 없이 정체하는 실패 방식이며,
> 대시보드가 이것을 드러내지 못하면 아무도 알아채지 못한다.

### §8.3 현황 화면  {#s8-3-status}

| 화면 | 담는 것 | 이 숫자가 말하는 것 |
|---|---|---|
| **지식베이스 현황** | 지식 항목 수, 출처 구성(소스코드 / QnA 비율), stale 비율, 미해결 모순 수, 최근 ingest 이력 | 지식이 자라고 있는가, 썩고 있는가 |
| **QnA 처리 현황** | 유입·처리량, **명시적 해결률 / 암묵적 해결 비율 / 미해결 종료율**(§6.3), 자동 게재 비율, 평균 후속 횟수 | 답변이 실제로 문제를 풀고 있는가 |
| **콘텐츠 현황** | 타입별 최근 발행·갱신 시점, 살아있는 문서의 stale 여부, 다음 발행 예정 | 콘텐츠가 최신인가 |
| **에이전트 운영 현황** | ingest 실행 이력과 실패, 검수 통과·반려 비율 | 파이프라인이 건강한가 |

**검수 반려율과 승격 거부율**은 품질 지표인 동시에 **신뢰 지표**다. 이 값이 높다는 것은
운영자가 에이전트의 산출물을 믿지 못하고 있다는 뜻이고, 낮은데도 오답이 나온다면
검수가 형식적으로 흐르고 있다는 뜻이다. 둘 다 사람이 읽어야 의미가 생긴다.

### §8.4 운영자는 감시자가 아니라 루프의 일부다  {#s8-4-operator-in-loop}

대기열의 행위는 모두 **루프로 되먹여진다.** 운영자가 일하지 않으면 루프가 느려지는
것이 아니라 **끊긴다.**

| 운영자 행위 | 루프에 미치는 효과 |
|---|---|
| 암묵적 해결을 확인 (Q6) | 봇 답변에 **ingest 자격이 생긴다** → 지식베이스가 자란다 |
| 승격 승인 (Q7) | 티켓 해결이 지식이 된다 → 루프가 닫힌다 |
| 모순 판정 (Q4) | 지식 품질이 회복된다 |
| 검수 승인·반려 (Q2·Q3) | 게재물의 품질이 결정된다 |
| 지식 공백에 우선순위 부여 (Q8) | 다음 ingest 방향이 정해진다 |

> 그래서 이 시스템의 처리량 상한은 로컬 LLM 의 속도가 아니라 **운영자가 대기열을
> 소화하는 속도**일 가능성이 높다. 대시보드 설계는 성능 문제이기도 하다.

### §8.5 짚어야 할 모순 — 누가 지식을 고치는가  {#s8-5-who-edits}

§4 는 "지식베이스는 사람이 손으로 쓰지 않는다, 에이전트가 짓는다"고 선언했다.
그런데 §8.2 의 Q4(모순 판정)와 Q5(정정)는 사람의 판단을 요구한다. **판단한 결과를
어떻게 반영하는가**가 정해지지 않았다.

| 후보 | 방식 | 장점 | 대가 |
|---|---|---|---|
| **A. 사람이 직접 편집** | 운영자가 지식 항목을 대시보드에서 고친다 | 즉시 반영, 정확 | 출처(provenance)가 끊긴다 — 그 내용의 근거가 무엇인지 추적 불가 |
| **B. 사람은 판정만, 반영은 에이전트** | 운영자는 "이쪽이 옳다"만 지정하고 에이전트가 문서를 고친다 | 출처 체계가 유지된다 | 한 단계 느리고, 에이전트가 의도를 오해할 수 있다 |

출처가 1급 시민이라는 §2 의 원칙을 지키려면 B 가 정합적이지만, 운영 현실에서 A 없이
버틸 수 있을지는 별개 문제다. **O27** 로 올린다.

## §9 시스템 아키텍처 (논리)  {#s9-architecture}

### §9.1 이 절이 정하는 것과 미루는 것  {#s9-1-scope}

아키텍처는 본래 M-003 설계 단계의 산출물이다. 다만 §1~§8 의 결정들이 **논리 구조를
이미 상당 부분 강제**하고 있으므로, 그 강제된 부분만 여기서 확정한다.

| 여기서 정한다 | M-003 으로 미룬다 |
|---|---|
| 컴포넌트와 그 책임 경계 | 언어 · 프레임워크 · 배포 형태 |
| 데이터가 어디에 사는가 (파일 / DB) | 구체적 DB 제품, 스키마 |
| 실행 경로의 분리 (온라인 / 배치) | 검색 구현 (키워드 / 임베딩 / 하이브리드) |
| 규칙이 집행되는 지점 | 로컬 LLM 런타임과 모델 선택 |

기술 선택을 미루는 이유는 **O1(코드베이스 규모) · O9(모델) · O11(지식 입도)** 이
아직 열려 있기 때문이다. 이것들을 모른 채 고른 기술은 근거 없는 선택이 된다.

### §9.3 컴포넌트 책임  {#s9-3-responsibilities}

| 컴포넌트 | 책임 | 근거 |
|---|---|---|
| **모 시스템 어댑터** | 모 시스템과의 모든 입출력을 이 한 겹에 가둔다 — 소스 읽기, QnA 읽기, 게재 쓰기 | 모 시스템은 교체 가능한 외부 의존이다 |
| **Raw 저장** | 수집 원본을 있는 그대로 보관 — 코드 스냅샷은 커밋에 고정, QnA 는 **계정과 해결 등급을 함께** | §2, §5.3 |
| **산출물 필터** | 이 시스템이 만든 것(봇 답변·콘텐츠)을 ingest 입력에서 걸러낸다. 사람 검증분만 통과 | §5.3 |
| **Ingest 오케스트레이터** | 변경 감지 → 재수집 범위 결정 → 구축 에이전트 호출 → 로그 적재 | §4 |
| **구축 에이전트** | 원천을 읽어 지식 항목을 짓고 갱신하며 모순을 표시 | §4 |
| **지식베이스** | 지식 항목의 보관·인덱싱·출처 추적·Lint | §3, §4 |
| **산출 오케스트레이터** | 트리거를 받아 5단계를 실행. 답변과 콘텐츠가 같은 실행기를 쓴다 | §5, §7.1 |
| **운영 도메인** | QnA 항목 상태 기계, 티켓, 콘텐츠 타입 레지스트리와 발행 이력, 통계 집계 | §6, §7.5 |
| **운영자 대시보드** | 대기열 여덟 종과 현황 네 종 | §8 |

### §9.4 저장소가 둘로 갈린다 — 지식은 파일, 운영은 DB  {#s9-4-two-stores}

이 시스템의 데이터는 성격이 전혀 다른 두 무리로 나뉘며, **같은 저장소에 두면 어느
한쪽이 망가진다.**

| | **지식베이스** | **운영 데이터** |
|---|---|---|
| 내용 | 지식 항목 | QnA 항목 상태, 티켓, 발행 이력, 통계 |
| 변경 성격 | 드물게, 묶음으로 (1 ingest = 1 커밋) | 잦게, 건건이 |
| 필요한 것 | 이력 · diff · additive merge · 사람이 읽는 형태 | 조건 질의 · 집계 · 동시성 · 트랜잭션 |
| 적합한 형태 | **파일 + 버전 관리** | **데이터베이스** |

**지식베이스를 파일로 두는 것은 취향이 아니라 §3 차용의 논리적 귀결이다.** llm-wiki 의
운영 모델(1 커밋 = 1 ingest, `log.md` append, additive merge, `[[wikilink]]`)과 OKF 의
번들 형식(디렉터리 = 번들, 1 파일 = 1 개념)은 **둘 다 파일 트리를 전제한다.** 지식을
DB 행으로 넣는 순간 차용한 운영 모델이 성립하지 않고, OKF 번들 내보내기는 별도
변환 작업이 된다.

반대로 QnA 항목 상태나 통계를 파일에 두면 조건 질의와 집계가 불가능해진다.
대시보드의 여덟 대기열은 전부 조건 질의다.

> **귀결**: 두 저장소를 잇는 것은 **출처(provenance)** 다. 운영 데이터의 QnA ID 와
> 지식 항목의 출처 필드가 서로를 가리키며, 이 연결이 stale 전파와 정정 추적의 경로가
> 된다. 출처가 1급 시민이어야 하는 이유가 여기서 구조로 드러난다.

### §9.5 실행 경로가 둘로 갈린다 — 온라인과 배치  {#s9-5-two-paths}

| | **온라인 경로** | **배치 경로** |
|---|---|---|
| 하는 일 | 질문 트리거 답변 산출 | Ingest, 콘텐츠 제작, Lint |
| 우선순위 | 지연 시간 | 정확도 · 처리량 |
| 자원 요구 | 짧고 잦은 추론 | 길고 무거운 추론 |

**둘은 같은 로컬 LLM 자원을 놓고 경쟁한다.** 대규모 ingest 가 도는 동안 질문이 들어오면
답변이 굶는다. 이것은 운영 중 반드시 마주칠 문제이고, 컨셉 단계에서 최소한 **경로가
분리되어 있다는 사실**은 확정해 둔다. 자원 배분 방식은 **O32**.

### §9.6 어댑터가 지키는 것  {#s9-6-adapter}

모 시스템과의 접점을 한 겹에 가두는 이유는 셋이다.

1. **교체 가능성** — 모 시스템의 QnA 구조가 바뀌어도 도메인 로직은 그대로다
2. **단일 출구** — 게재는 되돌릴 수 없는 대외 행위다(§5.2). 출구가 하나여야 감사 기록과 정정 추적이 성립한다
3. **전제의 격리** — §14 의 전제 2·3·7(계정 구분 · 후속 답글 · 게재 자리)은 전부 어댑터가 감당하는 가정이다. 전제가 깨지면 **어댑터만 다시 만들면 된다**

> 전제 1 은 "모 시스템은 하나"다. 어댑터를 두는 목적은 **다중 지원이 아니라 격리**이며,
> 다중 모 시스템은 현재 범위 밖이다.

### §9.7 규칙은 한 곳에서만 집행한다  {#s9-7-single-enforcement}

§5.3 의 되먹임 차단은 **산출물 필터 한 지점에서만** 집행한다. Ingest 를 부르는 경로가
여럿 생기더라도 필터를 우회하는 길은 두지 않는다.

규칙을 여러 곳에 흩어 두면 언젠가 한 곳이 새고, 새는 순간 **오답이 지식이 되어 굳는다.**
이것은 사후에 발견하기 어려운 종류의 고장이다 — 지식베이스는 틀린 채로도 잘 동작하는
것처럼 보이기 때문이다.

## §10 핵심 루프  {#s10-core-loop}

```
 ┌────────────── 모 시스템 (Parent System) ──────────────┐
 │  소스코드 저장소       QnA 게시판 (질문·답변·후속)      │
 └──────┬───────────────────────┬───────────────▲────────┘
        │ 변경 추적              │ 수집          │ ⑤게재
        ▼                       ▼               │
 ┌──────────────────  Raw Layer  ───────────────┼────────┐
 │  코드 스냅샷(커밋 고정)   QnA 원문 · 답변 이력 │        │
 │                       (계정 = 봇 / 사람, 해결 등급) │  │
 └──────┬───────────────────────┬───────────────┼────────┘
        │                       │ ※봇답변:해결분만│
        └────▶  Ingest (구축 에이전트)  ◀────────┘        │
                     │  pi 하네스 + 로컬 LLM              │
                     ▼                                    │
 ┌───────────  Wiki Layer = 지식베이스  ────────────────┐  │
 │  1 파일 = 1 지식 항목 · 출처(커밋 / QnA ID) · stale   │  │
 └────┬─────────────────────────────────┬──────────────┘  │
      │ ②조회                           │ Lint            │
      ▼                                 ▼                 │
 ┌─── 산출 파이프라인 (§5) ─────────┐  모순 · stale 검출   │
 │  ①분석  ②지식베이스 조회         │        │            │
 │  ③생성  ④검수 ── 반려 ──┐        │        └─▶ 정정 후보 ┤
 │  ⑤게재 ─────────────────┼────────┼─────────────────────┘
 │                          │        │
 │  ▲ 트리거 둘 (§7.1)      │        │
 │   · 질문 유입 → 답변      │        │
 │   · 주기·임계 → 콘텐츠 ───┼────────┼──▶ FAQ · 가이드(갱신)
 │     (§7)                 │        │    칼럼 · 뉴스레터(발행)
 └────────┬─────────────────┘        │
          │          └─▶ 티켓 ◀─── (모든 실패 경로)
          ▼                  │
   QnA 항목 추적 (§6)         └─▶ 사람이 해결 ─▶ 지식 승격 ─┐
          │                                                 │
          ├─ 후속/미해결 ─▶ 파이프라인 재실행 ↺              │
          ├─ 해결 ─▶ 종결 ─▶ 반복 탐지 ─▶ FAQ 승격           │
          └─ 미해결 종료 ─▶ 지식 공백으로 기록 ─▶ ingest 우선순위
                                                            │
      ◀─────────────────────────────────────────────────────┘
              (다음 질문의 답변 품질이 올라간다)
```

루프가 닫히는 지점은 **승격(Promotion)** 이다. 그리고 §5.3 의 봇 답변 배제가 없으면
같은 루프가 오답 증폭기가 된다 — 지식이 자라는 메커니즘과 오답이 자라는 메커니즘은
동일하기 때문이다.

## §11 액터  {#s11-actors}

| 액터 | 역할 | 이 시스템과의 관계 |
|---|---|---|
| **최종 이용자** | 모 시스템에서 질문하고, 게재된 답변을 읽고, 후속 질문을 단다 | 이 시스템을 직접 알지 못한다 |
| **모 시스템** | 소스코드와 QnA 이력을 제공하고, 이 시스템이 쓴 답변을 게재받는다 | 지식의 원천이자 **게재 대상**. 양방향 |
| **운영자** | §8.2 의 여덟 대기열을 소화한다 — 티켓·검수·모순·정정·암묵적 해결 확인·승격·지식 공백 | 프론트를 직접 쓰는 유일한 사람이자 **루프의 일부**. 여기서 못 하는 일은 아무도 못 한다 |
| **구축 에이전트** | 소스·QnA 를 읽어 지식 항목을 짓고 갱신·모순 표시 | 로컬 LLM + pi 하네스, 배치 실행 |
| **응답 에이전트** | 질문 트리거로 5단계 파이프라인 수행 | 온라인 경로. **봇 계정**으로 게재한다 |
| **콘텐츠 에이전트** | 주기·임계 트리거로 같은 5단계를 수행해 FAQ·가이드·칼럼·뉴스레터를 만든다 | 배치 경로. 역시 **봇 계정**으로 게재한다 |

> 프론트는 **운영자용 대시보드**다. 이용자는 모 시스템의 QnA 화면에서 게재된 답변을 볼 뿐이다.

## §12 핵심 용어  {#s12-glossary}

| 용어 | 정의 | 혼동 주의 |
|---|---|---|
| **모 시스템 (Parent System)** | 이 서브시스템이 부착되는 운영 중인 서비스 | 지식의 원천이자 게재 대상. 양방향 |
| **QnA 항목** | 질문 하나를 중심으로 답변·후속·상태를 묶은 **추적 단위** | 질문 1건이 아니라 *해결까지의 전 과정*이다 |
| **질문 (Question)** | 최종 이용자가 던진 원문 1건 | QnA 항목의 시작점일 뿐 |
| **후속 (Follow-up)** | 게재된 답변 뒤에 달리는 추가 질문·재질문·이의 | 파이프라인 재실행의 트리거 |
| **답변 초안 (Draft Answer)** | 검수 전, 근거가 붙은 채 대기하는 답변 | 아직 대외 산출물이 아니다 |
| **검수 (Review)** | 초안이 근거에 뒷받침되는지 확인하는 **필수 4단계** | 주체(사람/에이전트)는 O13 미결 |
| **게재 (Publish)** | 답변을 모 시스템 QnA 에 올려 이용자에게 노출하는 행위 | 이 시스템이 모 시스템에 가하는 **유일한 쓰기** |
| **봇 계정 (Bot Account)** | 이 시스템이 게재에 쓰는 전용 계정 | **조건부 ingest 배제의 식별 기준**. 내용이 아니라 계정으로 가른다 |
| **명시적 해결** | 사람(이용자·운영자)이 확인해 종결된 상태 | **검증 신호**. 봇 답변에 ingest 자격을 준다 |
| **암묵적 해결** | 사람 확인 없이 해결로 간주된 상태 (타임아웃·자체 판단) | 검증이 아니다. 통계엔 반영하되 **지식 원천으로 쓰지 않는다**. 사람 확인 시 명시적으로 **상향** |
| **등급 상향** | 암묵적 해결이 사람 확인을 받아 명시적 해결이 되는 전이 | 이 시점에 ingest 자격이 발생한다. 강등은 없다 |
| **QnA 기록** | 질문·답변·후속·상태의 시계열 기록 | 지식베이스가 **아니다**. ingest 원재료(Raw) |
| **지식 항목 (Knowledge Entry)** | 1 파일 1 개념. 출처·유효 범위·상태를 가진 인용 가능한 단위 | 소스 원문도 QnA 원문도 아닌 *가공물* |
| **지식베이스 (KB)** | 지식 항목의 집합 = Wiki Layer | |
| **Raw Layer** | 수집된 원본 (코드 스냅샷, QnA 원문) | 질의 대상이 아니라 ingest 입력 |
| **출처 (Provenance)** | 지식 항목·게재 답변이 유래한 커밋 해시 또는 QnA ID | 1급 시민 |
| **근거 (Grounding)** | 답변이 인용한 지식 항목 식별자 집합 | 신뢰의 최소 단위 |
| **Ingest / Query / Lint** | 원천→지식 생성 / 지식→답변 합성 / 정합성 검사 | llm-wiki 3 연산 차용 |
| **stale** | 출처 커밋이 최신 코드와 어긋나 신뢰할 수 없는 상태 | 삭제가 아니라 **표시**. 게재 답변에도 전파 |
| **모순 (Contradiction)** | 두 지식 항목이 양립 불가능한 주장을 하는 상태 | **양쪽을 남기고 표시**한다 |
| **승격 (Promotion)** | 티켓 해결·반복 QnA 를 지식 항목이나 FAQ 로 올리는 행위 | 루프를 닫는 유일한 연결 고리 |
| **정정 (Correction)** | 게재된 답변이 틀린 것으로 판명되어 고치는 행위 | 경로는 O14 미결 |
| **지식 공백** | 미해결로 종료된 QnA 가 가리키는, 지식베이스가 못 답하는 영역 | 버릴 데이터가 아니라 ingest 우선순위 신호 |
| **모 시스템 어댑터** | 모 시스템과의 모든 입출력을 가두는 한 겹 (소스 리더 · QnA 리더 · 게재 라이터) | 교체 가능성·단일 출구·전제 격리를 담당 (§9.6) |
| **산출물 필터** | 이 시스템이 만든 것을 ingest 입력에서 걸러내는 **단일 집행 지점** | §5.3 규칙이 사는 곳. 우회 경로를 두지 않는다 (§9.7) |
| **온라인 경로 / 배치 경로** | 질문 트리거 답변 산출 / Ingest·콘텐츠·Lint | 같은 로컬 LLM 자원을 놓고 경쟁한다 (§9.5) |
| **작업 대기열 (Queue)** | 운영자의 판단을 기다리는 항목의 묶음. 여덟 종 (§8.2) | 대시보드의 중심. 현황 숫자는 보조다 |
| **방치 비용** | 대기열을 처리하지 않을 때 발생하는 손해 | 대기열 우선순위의 기준. 사고를 내는 대기열과 조용히 정체시키는 대기열은 다르다 |
| **콘텐츠 (Content)** | 질문 없이 주기·조건으로 만들어 내보내는 산출물 (FAQ · 가이드 · 칼럼 · 뉴스레터 등) | 답변과 **같은 5단계 파이프라인**을 쓴다. 트리거만 다르다 |
| **살아있는 문서** | 항상 최신이어야 하는 콘텐츠 (FAQ · 가이드) | stale 되면 **갱신**한다 |
| **발행물** | 발행 시점의 스냅샷인 콘텐츠 (칼럼 · 뉴스레터) | 고칠 수 없다. 후속 발행으로만 바로잡는다 |
| **콘텐츠 타입** | 주 입력 · 트리거 · 성격 · 게재처 · 검수 강도 다섯 가지를 선언한 등록 단위 | 확장은 구현이 아니라 **선언 추가**여야 한다 |
| **FAQ** | 반복도가 높고 해결된 QnA 를 승격시켜 만든 공개용 문답 | QnA 분포의 파생물. 승격은 재료 선별, 문서화는 콘텐츠 파이프라인의 일 |
| **티켓 (Ticket)** | 사람 손이 필요한 작업 단위. 파이프라인의 모든 실패 경로가 수렴한다 | **이 시스템이 직접 소유한다.** QnA 항목과의 관계는 O17 |
| **Knowledge Bundle** | 지식베이스를 자기완결적 디렉터리로 담은 배포 단위 (OKF 차용) | 운영 데이터는 포함하지 않는다 |

## §13 시스템 경계  {#s13-boundary}

### 이 시스템이 **소유**하는 것

- 지식베이스 — 지식 항목의 모델과 수명주기 (생성 · 갱신 · stale · 폐기)
- Raw Layer — 소스코드 보유본과 최신 상태 추적, QnA 이력 수집본
- Ingest / Query / Lint 3 연산과 그것을 수행하는 에이전트 파이프라인
- 모 시스템 어댑터 — 소스 리더 · QnA 리더 · 게재 라이터
- 산출 5단계 파이프라인 (분석 · 조회 · 생성 · 검수 · 게재) — 답변과 콘텐츠 공통
- 콘텐츠 제작 — FAQ · 사용 가이드 · 칼럼 · 뉴스레터의 작성·갱신·발행과 타입 확장 구조
- **QnA 항목의 수명주기와 해결까지의 추적**
- 티켓과 그 상태 기계 — 외부 ITSM 에 위임하지 않는다
- 게재 답변의 사후 정정 추적
- QnA 기록과 그로부터 나온 통계
- 콘텐츠의 수명주기 — 살아있는 문서의 갱신, 발행물의 회차 누적
- 운영자용 프론트 — **작업 대기열 여덟 종**(§8.2)과 현황 화면 네 종(§8.3)
- 지식베이스의 OKF 번들 내보내기

### 이 시스템이 **소유하지 않는** 것

- 최종 이용자의 계정 · 인증 · 권한 — 모 시스템의 책임이다
- 최종 이용자 대면 UI — 모 시스템이 렌더링한다. 우리는 그 화면에 **답변과 콘텐츠를 올릴 뿐** 화면 자체를 만들지 않는다
- 모 시스템의 도메인 데이터와 비즈니스 로직
- **모 시스템의 소스코드에 대한 쓰기** — 읽고 추적할 뿐, 고치거나 PR 을 내지 않는다
- 모 시스템에 대한 그 밖의 쓰기 조치 — 허용된 쓰기는 **답변 게재와 콘텐츠 게재 둘뿐**이다 (게재처 목록은 O21 에서 확정)
- 외부 ITSM 도구 연동
- LLM 모델 자체의 학습 · fine-tuning

## §14 이 컨셉이 서 있는 전제  {#s14-assumptions}

1. 모 시스템은 하나이며, 소스코드 읽기 접근과 QnA 게시판 **쓰기 접근**이 확보된다
2. 모 시스템의 QnA 는 **게재자 계정을 구분해 보관**한다 — §5.3 규칙이 이것에 의존한다
3. 모 시스템의 QnA 는 **후속 답글이 가능**하다 — §6 추적이 이것에 의존한다
4. 소스코드를 외부 API 로 보내지 않는다 — 그래서 구축 경로는 로컬 LLM 이다
5. 초기 지식베이스는 비어 있다 — 콜드 스타트가 기본 상태이고, 소스코드 ingest 가 첫 채움을 담당한다
6. 티켓을 처리할 사람이 존재한다 (최소 운영자 본인)
7. 콘텐츠를 올릴 자리(FAQ 면·문서 면·발송 경로)가 모 시스템 쪽에 존재하거나 마련된다
8. 실서비스이므로 오답 비용이 실재한다 — 근거 없는 게재보다 "모른다 + 티켓"이 낫다

> 전제 2·3·7 은 **모 시스템에 대한 요구사항**이다. 충족되지 않으면 §5.3 · §6 · §7 을
> 다시 설계해야 하므로, M-002 요구사항 단계에서 가장 먼저 확인할 항목이다.

## §15 미결 쟁점  {#s15-open-questions}

| # | 쟁점 | 왜 컨셉에 영향을 주는가 |
|---|---|---|
| **O1** | 모 시스템의 도메인과 규모 (코드베이스 크기·언어) | ingest 전략과 지식 항목 입도가 갈린다 |
| **O2** | 연동 계약의 형태 — 수집(읽기)과 게재(쓰기) 각각 | API / DB 직결 / 이벤트 중 무엇인지 |
| **O3** | 각 등급에 무엇이 들어가는가 — 명시적 해결로 인정할 **구체적 신호**(이용자 버튼 / 운영자 종결 / 그 밖) | 등급 구분 자체는 **확정**(§5.3.1). 남은 것은 편입 기준이며, 모 시스템 QnA 가 어떤 신호를 제공하는지(O2)에 종속된다 |
| **O4** | 승격이 자동인가 사람 승인인가 | 오답 증식 위험 대 운영 부담 |

| **O6** | 최종 이용자 식별 방식 | 이력 기반 답변과 개인정보 취급 범위가 갈린다 |
| **O7** | 다국어 여부 | 지식 항목 단위와 검색 설계가 달라진다 |
| **O8** | 통계의 소비자와 핵심 지표 | 지표가 곧 프론트 화면 정의다. **등급별 분리 집계는 확정**(§6.3) 이고, 남은 것은 세부 정의와 임계값 |
| **O9** | 구축 에이전트와 응답 에이전트가 같은 모델인가 | 로컬 LLM 사양·배치 주기·지연 예산 |
| **O10** | 소스코드 보유 형태와 동기화 주기 | Raw Layer 설계와 stale 판정 지연 |
| **O11** | 지식 항목의 입도 (파일 / 함수 / 기능 단위) | 검색 품질과 ingest 비용의 트레이드오프 |
| **O12** | OKF 번들을 실제로 내보낼 대상이 있는가 | 없다면 형식 준수를 뒤로 미룰 수 있다 |
| **O13** | **검수(4단계)의 주체** — 에이전트 자체 검증 / 사람 승인 / 근거 충분성 임계 기반 혼합 | 단계는 확정됐고 주체만 남았다. 운영 부담과 오답 노출의 트레이드오프이며 프론트 화면까지 바꾼다 |
| **O14** | 게재 후 정정 경로 — 수정 게재 / 철회 / 정정 코멘트 | 모 시스템 QnA 가 무엇을 허용하는지에 종속 |
| **O15** | 봇 계정의 답변자 표기 — 이용자가 "AI 가 쓴 답변"임을 아는가 | §5.3 이 계정 분리를 이미 요구한다. 남은 것은 노출 정책 |
| **O16** | 답변 게재의 지연 예산 (즉시 / 분 단위 / 배치) | 응답 에이전트를 온라인 경로로 둘지 배치로 둘지 |
| **O17** | **QnA 항목과 티켓이 하나인가 둘인가** (§6.4 A안 / B안) | 데이터 모델 전체가 여기서 갈린다 |
| **O18** | 추적의 강제 종료 조건 — 무응답 타임아웃이 있는가, 얼마인가 | 없으면 QnA 항목이 영원히 열려 있어 통계가 왜곡된다. 타임아웃 해결은 §5.3.1 상 **암묵적 해결**이므로 ingest 자격이 없다 |
| **O19** | 후속이 달렸을 때 재실행 트리거 — 즉시 / 폴링 / 이벤트 | O2 연동 형태와 맞물린다 |

| **O22** | **뉴스레터 구독자 명단을 누가 소유하는가** | "이용자 개인정보는 모 시스템의 것"이라는 경계와 충돌한다 (T3). 개인정보 취급 범위가 걸린다 |
| **O23** | 콘텐츠 타입별 발행 주기와 임계 조건 | 배치 스케줄과 로컬 LLM 자원 계획이 여기서 나온다 |
| **O24** | **콘텐츠 검수 주체와 강도** — 발행물은 살아있는 문서보다 엄격해야 하는가 | 회수 불가능한 발행물의 오류 비용이 답변보다 크다. O13(답변 검수)과 별개로 정해야 할 수 있다 |
| **O25** | 운영자가 몇 명이며 **역할 분리가 있는가** (검수자 / 티켓 처리자 / 승인자) | 1인이면 대기열 여덟 개가 한 사람에게 쏟아진다. 대시보드 구성과 권한 모델이 갈린다 |
| **O26** | 대기열 우선순위를 **시스템이 제시할 것인가**, 운영자가 스스로 고르는가 | 여덟 개를 나란히 두면 위험한 대기열이 묻힌다 (§8.2) |
| **O27** | **누가 지식 항목을 고치는가** — 사람 직접 편집(A) / 사람은 판정만 하고 에이전트가 반영(B) | 출처 추적 체계의 유지 여부가 걸린다 (§8.5) |
| **O28** | 위험 대기열(Q4·Q5)이 쌓일 때 **알림이 있는가**, 어떤 경로인가 | 없으면 대시보드를 열지 않는 날에는 아무도 모른다 |
| **O29** | 이 시스템의 처리량 상한이 **운영자 소화 속도**라면, 그 병목을 어디까지 자동화할 것인가 | 자동화할수록 사람 검증이 줄어 §5.3 되먹임 차단이 약해진다 — 정면 트레이드오프 |
| **O30** | 지식베이스의 버전 관리를 **git 으로 할 것인가** | 파일 저장은 §9.4 에서 확정. 남은 것은 이력 관리 수단이며, llm-wiki 의 "1 커밋 = 1 ingest"를 그대로 쓸지가 걸린다 |
| **O31** | 지식 검색 방식 — 키워드 / 임베딩 / 하이브리드 | O11(입도)·O1(규모)에 종속. 로컬 LLM 자원 계획과도 맞물린다 |
| **O32** | 온라인·배치가 **로컬 LLM 자원을 어떻게 나눠 쓰는가** | 대규모 ingest 중 답변이 굶는 문제. 별도 인스턴스 / 우선순위 큐 / 시간대 분리 |
| **O33** | 운영 데이터와 지식베이스의 **일관성 수준** — 출처 링크가 깨졌을 때 어떻게 감지·복구하는가 | 두 저장소를 잇는 것이 출처인데, 그 링크의 무결성을 보장하는 주체가 없다 |
