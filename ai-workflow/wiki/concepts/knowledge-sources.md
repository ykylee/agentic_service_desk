# Agentic Service Desk — 지식의 원천과 구축

- 문서 목적: 지식이 어디서 오고(소스 저장소·QnA), 어떤 외부 컨셉을 빌려 왔으며(llm-wiki·OKF), 에이전트가 그것을 어떻게 짓는가.
- 담는 절: §2 · §3 · §4 (절 번호는 컨셉 문서 전체에서 전역으로 유일하다)
- 대상 독자: AI agent, 저장소 maintainer
- 상태: draft
- 최종 수정일: 2026-08-28
- 허브: [`agentic-service-desk-concept`](./agentic-service-desk-concept.md) — **먼저 읽는다**

## §2 지식의 두 원천  {#s2-two-sources}

이 시스템이 다른 QnA 봇과 갈라지는 지점은 지식 원천이 **둘**이고, 그 둘의 성격이
근본적으로 다르다는 것이다.

| | **소스 저장소** (코드 + 히스토리) | **QnA·답변 이력** |
|---|---|---|
| 원천의 성격 | 실행되는 진실 (ground truth) | 관찰된 현상 |
| 답하는 질문 | "실제로 어떻게 동작하는가" (코드) · "왜 그렇게 정했는가" (히스토리) | "사람들이 실제로 무엇을 묻는가" |
| 정확도 | 그 자체가 동작의 정의 | 과거 답변이 틀렸을 수 있다 |
| 변화 감지 | 커밋 diff | 새 질문 유입 · 표현 변화 |
| 파생 지식 | 기능 · API · 제약 · 에러 원인 · **결정의 근거** | FAQ · 사용자 표현 사전 · 질문 빈도 |
| 신선도 관리 | 커밋 추적으로 **자동 stale 판정 가능** | 시간 경과 · 코드 변경에 의해 무효화 |
| **답하지 못하는 것** | 운영 관행, 저장소 밖에서 내려진 결정, **현재 설정값**(지식이 아니라 상태 — §2.2.2) | 아직 아무도 묻지 않은 것 |

두 원천은 **교차 검증**된다. 이것이 이 구조의 실익이다.
(단 1국면에서는 QnA 쪽이 비어 있어 성립하지 않는다 — §1.3)

- QnA 이력의 답변이 맞는지를 **소스코드 지식으로 소급 검증**할 수 있다
- 소스코드가 바뀌면 그에 근거했던 **기존 FAQ·게재 답변이 자동으로 의심 대상**이 된다
- 사용자가 쓰는 표현(QnA)과 코드의 식별자(소스) 사이의 **어휘 격차**를 이 시스템이 메운다

> **핵심 설계 함의**: 모든 지식 항목은 자기가 **어느 커밋 / 어느 QnA 에서 왔는지**를
> 들고 있어야 한다. 출처 추적이 없으면 stale 판정도, 교차 검증도, 근거 부착도
> 불가능하다. 출처는 메타데이터가 아니라 **1급 시민**이다.

### §2.1 두 원천의 커버리지 공백  {#s2-1-coverage-gap}

사내 업무 시스템(§1.1)이라는 사실이 이 구조에 구멍 하나를 드러낸다.

사내 시스템 질문의 상당수는 **"이 값이 왜 이렇게 나오나"** 같은 업무 규칙 질문이다.
소스코드는 *어떻게 동작하는가*를 정확히 답하지만, **왜 그렇게 정해졌는가**는 답하지
못한다. 그 근거는 흔히 코드가 아니라 **설정 데이터 · 운영 관행 · 사람의 기억**에 있다.

| 질문 유형 | 소스코드로 답하는가 |
|---|---|
| "이 기능은 어떻게 동작하나" | **그렇다** |
| "이 오류는 왜 나나" | 대체로 그렇다 |
| "이 값은 왜 이 기준으로 계산되나" | **아니다** — 규칙의 근거는 코드 밖에 있을 수 있다 |
| "이럴 때는 어떻게 하는 게 맞나" | **아니다** — 운영 관행이다 |

### §2.2 "세 번째 원천"은 하나가 아니다  {#s2-2-third-source-candidates}

공백을 메울 후보를 하나로 뭉뚱그리면 판단이 틀린다. **셋으로 나누면 답이 각각 다르다.**

| | **B1. 저장소 히스토리** | **B2. 설정 데이터** | **B3. 운영 문서** |
|---|---|---|---|
| 무엇인가 | 커밋 메시지 · PR 설명 · 이슈 | 설정 파일 · 환경변수 · DB 설정값 | 사내 위키 · 업무 매뉴얼 · 규정 |
| 답하는 것 | **왜 그렇게 정했는가** | 지금 값이 무엇인가 | 이럴 때 어떻게 하는가 |
| 수집 비용 | **거의 없다** — 이미 접근 중인 저장소 안에 있다 | 낮다 | 중간 |
| 출처 추적 | **커밋에 묶인다** — 기존 체계 그대로 | 가능 (값 변경 감지) | **불가** — 낡음을 판정할 기준이 없다 |
| 변동성 | 불변 (히스토리는 덮이지 않는다) | **높다** — 운영 중 수시로 바뀐다 | 낮지만 조용히 낡는다 |
| 위험 | 커밋 위생이 나쁘면 값이 없다 | 민감정보 혼입 · 즉시 stale | **낡은 규정이 근거로 인용된다** |

#### §2.2.1 B1 은 새 원천이 아니라 안 쓰던 절반이다  {#s2-2-1-history}

지금까지 "소스코드 원천"이라고 부른 것은 사실 **코드만**이었다. 저장소에는 코드와
**히스토리**가 함께 있고, "왜 그렇게 정했는가"는 흔히 **커밋 메시지와 PR 설명에
남는다.** 우리는 이미 그 저장소를 읽고 있다.

- 원천이 늘어나는 것이 아니라 **가진 원천을 온전히 쓰는 것**이다
- **출처 체계가 그대로 작동한다** — 커밋 해시가 이미 1급 시민이다(D3)
- 히스토리는 덮이지 않으므로 **stale 관리가 따로 필요 없다**

> 다만 값은 **커밋 위생에 비례한다.** 메시지가 "fix", "update" 뿐이면 얻을 것이 없다.
> 채택 전에 실제 히스토리를 표본으로 확인해야 한다 (**O41**).

#### §2.2.2 B2 는 ingest 대상이 아니라 조회 대상이다  {#s2-2-2-config}

설정 데이터는 성격이 다르다. **자주 바뀌는 값을 지식 항목으로 굳히면 굳는 순간
stale 이 된다.** 지식베이스는 *변하지 않는 이해*를 담는 곳이지 *현재 상태*를 담는
곳이 아니다.

> **구분**: **지식**("승인 한도는 부서 등급으로 결정된다")과
> **현재 상태**("지금 이 부서의 한도는 300만 원이다")는 다른 것이다.
> 전자는 ingest 하고, 후자는 필요할 때 **조회**한다.

이 구분을 세우지 않으면 지식베이스가 설정값 미러가 되고 stale 대기열이 폭주한다.
조회 경로를 둘지는 §2.4 와 **O42** 에서 다룬다.

#### §2.2.3 B3 은 출처 체계를 깨뜨린다  {#s2-2-3-ops-docs}

운영 문서는 사람이 쓴 것이라 **낡았는지 판정할 방법이 없다.** §2 의 stale 판정은
"출처 커밋이 최신 코드와 어긋났는가"로 성립하는데, 사내 위키 문서에는 대응하는
커밋이 없다.

이것이 D3(출처는 1급 시민)와 정면으로 부딪힌다. 낡은 규정이 **근거로 인용되어**
답변에 실리면, 근거가 붙어 있다는 사실이 오히려 오답을 그럴듯하게 만든다.

### §2.3 확정 — 셋을 다르게 다룬다  {#s2-3-decision}

| 후보 | 처리 | 근거 |
|---|---|---|
| **B1 저장소 히스토리** | **지금 원천에 포함한다** | 새 원천이 아니라 미사용 절반. 출처 체계 그대로, stale 관리 불필요, 비용 거의 없음 |
| **B2 설정 데이터** | **ingest 하지 않는다.** 필요하면 조회 경로로 다룬다 | 지식이 아니라 현재 상태다. 굳히면 즉시 stale |
| **B3 운영 문서** | **A 로 간다 — 티켓으로 보내고 승격으로 메운다** | 출처 추적이 불가해 D3 를 깨뜨린다. 필요할 때 사람이 확인한 내용만 지식이 된다 |

즉 **A 와 B 중 택일이 아니었다.** 히스토리는 지금 들이고, 설정은 ingest 하지 않으며,
운영 문서만 A(티켓 승격)로 남긴다. 셋 다 확정이다.

이렇게 하면 "왜 그렇게 정했는가"의 상당 부분을 **출처 체계를 깨지 않고** 얻는다.
남는 공백(운영 관행)은 원래 설계된 경로대로 티켓이 흡수하며, 1국면에서는 그것이
이미 지식 성장의 주 경로다(§1.3).

### §2.4 범위 밖 — "내 데이터" 질문  {#s2-4-out-of-scope}

§2.2.2 의 구분에서 따라 나오는 경계가 하나 더 있다. 사내 업무 시스템에는
**"내 OO 는 어떻게 되어 있나요"** 형태의 질문이 반드시 들어온다.

| 질문 | 종류 | 이 시스템이 답하는가 |
|---|---|---|
| "승인 한도는 어떤 기준으로 정해지나요" | 지식 | **답한다** |
| "제 승인 한도는 얼마인가요" | 개인 데이터 조회 | **답하지 않는다** |

후자는 지식 부족이 아니라 **권한과 실시간성의 문제**다. 이용자별 데이터를 읽으려면
개인 권한을 위임받아야 하고, 그 순간 §13 경계("이용자의 계정·권한은 모 시스템의
것")가 무너진다.

> **확정**: 개인 데이터 조회 질문은 **범위 밖**이며 티켓으로 보낸다. 다만 이 유형이
> 실제 질문에서 큰 비중을 차지한다면 별도 기능으로 다시 검토한다 (**O42**).

이 경계를 명시하지 않으면 "조회만 하면 되는데"라는 요청이 조금씩 들어와 범위가
모 시스템 쪽으로 번진다.
## §3 차용하는 외부 컨셉 — llm-wiki 와 OKF  {#s3-borrowed}

둘은 경쟁 개념이 아니라 **층이 다르다**. 겹치지 않게 역할을 나눠 쓴다.

| | **llm-wiki** | **OKF (Open Knowledge Format)** |
|---|---|---|
| 차용하는 층 | **운영 모델** — 지식이 어떻게 들어오고 질의되고 정리되는가 | **교환 형식** — 지식을 어떻게 자기완결적으로 담고 내보내는가 |
| 핵심 구조 | 3-layer: Raw → Wiki → Schema | Knowledge Bundle = 디렉터리 하나 |
| 핵심 연산 | Ingest / Query / Lint | (연산 없음 — 형식 규약만) |
| 단위 | 페이지, `[[wikilink]]` 로 연결 | 1 파일 = 1 개념, 파일 경로 = 개념 ID |
| 메타데이터 | frontmatter + `related_pages` | YAML frontmatter, `type` 필수 |
| 예약 파일 | `index.md`, `log.md` | `index.md`, `log.md` (동일) |
| 방향성 | `PURPOSE.md` (4-element) 가 ingest/query 를 조향 | 없음 |
| 소비자 규약 | 없음 | **MUST NOT reject** — 필드 누락·미지의 타입·깨진 링크에도 소비 실패 금지 |

**우리의 합성**:

- **내부 운영은 llm-wiki 규칙**을 따른다 — Ingest / Query / Lint 3연산, `log.md` append,
  모순 플래그, additive merge, 그리고 stale 검사.
- **외부로 나가는 형식은 OKF 번들**로 담는다 — 지식 항목만이 번들의 내용물이고,
  티켓·QnA 기록 같은 운영 데이터는 포함하지 않는다.
- llm-wiki 의 `PURPOSE.md` 개념은 **모 시스템별 방향성 선언**으로 재사용한다.

> **차용의 원칙**: 개념만 흡수하고 코드는 가져오지 않는다. OKF 는 Apache 2.0 이지만
> 우리 형식은 우리 spec 으로 재정의한다.
## §4 에이전트 기반 지식베이스 구축  {#s4-agent-build}

지식베이스는 사람이 손으로 쓰지 않는다. **에이전트가 짓는다.**

| 항목 | 선택 | 근거 |
|---|---|---|
| 하네스 | **pi 같은 최소 하네스** | "Primitives, not features" — 마크다운 지시문 + 도구 직접 호출 |
| 모델 | **로컬 LLM** | ① 소스코드를 외부로 내보내지 않는다 ② 지속·대량 ingest 비용이 0 에 수렴 ③ 오프라인 재현 가능 |
| 실행 형태 | 배치 ingest + 변경 트리거 | 커밋 유입 시 해당 범위만 재수집 |
| 초기 적재 | **1회 전체 부트스트랩** | 중규모(§1.1)라 감당 가능하다. 이후는 증분이 기본 |
| 다언어 대응 | 언어별 파서 없이 **LLM 이 코드를 읽어 개념 추출** | 언어 수만큼 도구를 만들지 않는다. 입도는 **언어 중립 단위**(파일·모듈·기능)로 잡는다 |

**Ingest 절차** (llm-wiki §2 차용):

1. **원천 읽기** — 변경된 소스 범위와 **그 커밋의 메시지·PR 설명**(§2.2.1), 또는 신규 QnA 묶음 (**봇 계정 답변은 해결 확정분만** — §5.3)
2. **대상 지식 항목 식별** — 새로 만들 것과 갱신할 것
3. **다중 항목 갱신** — 충돌 시 폐기하지 않고 **양쪽을 남기고 모순 표시**
4. **로그 적재** — `log.md` 에 한 줄, 1 회 ingest = 1 커밋

**Lint** 는 주기적으로 돈다: 모순 미해결 / stale / 고아 항목 / 끊어진 링크 / 참조 부재.
**소스코드 원천이 있으므로 stale 판정이 시간이 아니라 커밋 기준으로 정확해진다** —
이것이 일반 위키 대비 이 시스템의 우위다.

> **역할 분리**: 지식을 *짓는* 에이전트와 답변을 *쓰고 게재하는* 에이전트는 다른 실행
> 경로다. 전자는 배치·정확도 우선, 후자는 온라인·저지연 우선. 같은 모델을 쓸지는 O9.
