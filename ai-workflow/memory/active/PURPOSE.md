- 대상 독자: AI agent, 저장소 maintainer
- 상태: draft (v10) — 컨셉 노트 v0.9 (논리 아키텍처) 와 정합. 미결 쟁점 O1~O33 이 닫히면 갱신한다.
- 최종 수정일: 2026-08-27
- 관련 문서: [컨셉 노트](../../wiki/concepts/agentic-service-desk-concept.md), [PROJECT_PROFILE.md](../../../docs/PROJECT_PROFILE.md), [roadmap M-001](./roadmap/M-001-concept.md)

> **개정 이력**
> - v1: 프로젝트명만 보고 "사내 IT 헬프데스크"로 추정 — **사실과 달라 폐기**
> - v2: 고객 QnA 서브시스템으로 재작성
> - v3: 무게중심을 **지식베이스 구축**으로 이동. 소스코드가 지식의 1차 원천으로
>   추가되고, llm-wiki · OKF 차용과 로컬 LLM 기반 에이전트 구축이 들어왔다.
> - v4: **답변 자동 작성·게재**가 대표 기능으로 확정. 모 시스템과의 관계가
>   단방향(수집)에서 **양방향(수집 + 게재)** 으로 바뀌었다.
> - v5: 답변 **5단계 규칙**(분석·조회·생성·검수·게재) 확정, 되먹임 차단이
>   **봇 계정 답변 ingest 배제**로 확정, QnA 가 **해결까지 추적되는 상태 엔터티**가 되었다.
> - v6: 봇 답변 배제가 **조건부**로 완화 — 해결 확정분은 지식에 반영한다. 되먹임
>   차단의 안전성이 **해결 판정의 강도**에 종속되었다.
> - v7: **해결 등급(명시적 / 암묵적) 확정.** ingest 자격은 명시적 해결에만 부여하고,
>   해결률 지표도 등급별로 분리 집계한다.
> - v8: **콘텐츠 제작이 두 번째 산출 축**으로 들어왔다 — FAQ·가이드·칼럼·뉴스레터를
>   주기적으로 제작·갱신·게재하며, 5단계 파이프라인이 답변 전용에서 공통 절차가 되었다.
> - v9: **운영자 대시보드**를 작업 대기열 중심으로 정리. 운영자가 감시자가 아니라
>   루프의 일부임이 드러났다.
> - v10: **논리 아키텍처** 확정 — 저장소가 지식(파일)과 운영(DB)으로, 실행 경로가
>   온라인과 배치로 갈린다. 기술 선택은 M-003 으로 미룬다.

## 1. Goals

이 프로젝트가 도달하려는 목표.

- **G1**: 모 시스템의 **소스코드**와 **QnA·답변 이력** 두 원천을 지속 수집해 하나의 지식베이스로 구축한다
- **G2**: 소스코드의 최신 상태를 추적하여, 코드가 바뀌면 그에 근거한 지식 항목이 stale 로 드러나게 한다
- **G3**: 지식베이스 구축을 **에이전트가 수행**하게 한다 — pi 같은 최소 하네스 위에서 **로컬 LLM** 으로 돌려, 소스코드를 외부로 내보내지 않고 지속 ingest 한다
- **G4**: **분석 → 지식베이스 조회 → 생성 → 검수 → 게재** 5단계를 이 시스템의 **모든 산출물에 공통으로** 적용한다. 단계를 건너뛰지 않으며, 모든 실패 경로는 티켓으로 수렴한다
- **G4-1**: 질문 유입을 트리거로 **QnA 답변을 자동 게재한다** — 첫 번째 산출 축
- **G5**: **각 QnA 항목을 해결로 처리될 때까지 추적한다** — 답변 게재는 종료가 아니라 과정이며, 후속이 달리면 파이프라인을 재실행한다. 게재 답변은 근거가 stale 되면 정정 후보로 올라온다
- **G6**: 자동 게재로 닫히지 않은 질문을 이 시스템이 직접 소유하는 티켓으로 관리하고, 해결 내용을 지식 항목으로 승격시킨다
- **G7**: 반복 질문을 탐지해 FAQ 로 승격시켜, QnA 분포가 곧 FAQ 가 되게 한다
- **G8**: 운영자용 프론트를 **작업 대기열 중심**으로 제공한다 — 티켓·검수(답변/콘텐츠)·모순·정정 후보·암묵적 해결 확인·승격 후보·지식 공백 여덟 대기열과, 지식베이스·QnA·콘텐츠·에이전트 운영 네 현황 화면
- **G9**: **봇 계정으로 게재한 답변을 원칙적으로 ingest 원천에서 배제**해 에이전트가 자기 산출물을 다시 학습하지 않게 하되, **명시적으로 해결된 답변은 검증된 것으로 보아 지식에 반영한다** — 배제되는 동안에도 기록·통계·FAQ 후보로는 남긴다
- **G10**: 해결을 **명시적 / 암묵적 두 등급**으로 판정하고, 지표를 등급별로 분리 집계해 무응답 이탈이 성공으로 집계되지 않게 한다
- **G11**: 주기·임계를 트리거로 **콘텐츠를 제작·갱신·게재한다** — 두 번째 산출 축. QnA 통계 기반 **FAQ**, 지식베이스 기반 **시스템 사용 가이드**, 주기 발행하는 **칼럼**과 **뉴스레터**
- **G12**: 콘텐츠 타입을 **선언으로 확장 가능하게** 만든다 — 주 입력·트리거·성격(살아있는 문서/발행물)·게재처·검수 강도 다섯 가지만 선언하면 같은 파이프라인이 돌아간다

## 2. Key Questions

이 저장소가 답하려는 핵심 질문:

- **Q1**: 소스코드를 어떤 입도로 지식 항목화해야 검색 품질과 ingest 비용이 균형을 이루는가?
- **Q2**: 코드가 바뀌었을 때 그에 파생된 지식 항목·FAQ·과거 답변을 어떻게 자동으로 의심 대상으로 만드는가?
- **Q3**: 소스코드 지식과 QnA 지식이 충돌할 때 무엇을 우선하고, 모순을 어떻게 드러내는가?
- **Q4**: 로컬 LLM 의 성능 한계 안에서 지식 항목의 품질을 어떻게 담보하는가?
- **Q5**: 지식베이스가 비어 있는 콜드 스타트에서, 소스코드 ingest 만으로 어디까지 답할 수 있는가?
- **Q6**: 질문이 "해결됐다"는 것을 무엇으로 판정하는가 — 그 판정이 모든 통계의 분모다
- **Q7**: 승격 시 오답이 자기 증식하지 않도록 무엇을 검문하는가?
- **Q8**: 검수(4단계)를 누가 수행해야 오답 노출과 운영 부담이 균형을 이루는가?
- **Q9**: QnA 항목과 티켓은 하나의 엔터티인가 둘인가 — 추적 단위를 무엇으로 잡는가?
- **Q10**: 이미 게재된 답변이 틀린 것으로 판명되면 어떤 경로로 정정하는가?
- **Q12**: 해결되지 못한 채 종료된 QnA(지식 공백)를 어떻게 ingest 우선순위로 되돌리는가?
- **Q13**: 명시적 해결로 인정할 구체적 신호는 무엇인가 — 모 시스템 QnA 가 어떤 확인 수단을 제공하는가에 종속된다
- **Q14**: 암묵적 해결 비율이 오를 때 그것이 이탈 신호인지 표시 누락인지를 무엇으로 가려내는가?
- **Q15**: 칼럼처럼 해석·의견이 필요한 콘텐츠에 "근거 없으면 내보내지 않는다" 원칙을 어떻게 적용하는가?
- **Q16**: 회수 불가능한 발행물(뉴스레터)의 검수는 갱신 가능한 문서와 어떻게 달라야 하는가?
- **Q17**: 운영자가 대기열을 소화하지 못할 때 시스템은 어떻게 그 정체를 드러내는가?
- **Q18**: 사람의 판단(모순 해소·정정)을 반영하면서도 지식 항목의 출처 추적을 어떻게 유지하는가?
- **Q11**: 모 시스템과 어떤 계약으로 붙어야, 모 시스템이 바뀌어도 이 시스템이 살아남는가?

## 3. Research Scope

### 포함 영역

- 지식베이스 — 지식 항목 모델, 출처(provenance) 추적, 수명주기 (생성 · 갱신 · stale · 폐기)
- Raw Layer — 모 시스템 소스코드 보유본과 최신 상태 추적, QnA·답변 이력 수집
- Ingest / Query / Lint 3 연산 (llm-wiki 운영 모델 차용)
- OKF Knowledge Bundle 형식으로의 지식베이스 내보내기
- 에이전트 기반 구축 파이프라인 — pi 계열 최소 하네스, 로컬 LLM, 배치·변경 트리거
- 소스코드 지식과 QnA 지식의 교차 검증 · 모순 표시
- 지식 검색과 근거 부착 답변 생성 (RAG)
- 산출 5단계 파이프라인 — 분석 · 지식베이스 조회 · 생성 · 검수 · 게재 (답변과 콘텐츠 공통)
- 콘텐츠 제작 — FAQ · 시스템 사용 가이드 · 칼럼 · 뉴스레터의 작성 · 갱신 · 발행
- 콘텐츠 타입의 확장 구조 (주 입력 · 트리거 · 성격 · 게재처 · 검수 강도 선언)
- 살아있는 문서의 갱신과 발행물의 회차 누적
- QnA 항목의 수명주기와 해결까지의 지속 추적, 후속 발생 시 파이프라인 재실행
- 봇 계정 답변의 조건부 ingest 배제 규칙 — 해결 확정 시 해제, 미해결 중에도 기록·통계·FAQ 후보로는 포함
- 해결 판정의 등급 구분 (명시적 / 암묵적) 과 등급별 ingest 자격, 암묵→명시 상향 경로
- 등급별 분리 집계 지표 (명시적 해결률 · 암묵적 해결 비율 · 미해결 종료율)
- 게재 답변의 사후 정정 추적
- 미해결 종료 QnA 를 지식 공백으로 기록하고 ingest 우선순위로 되먹이는 경로
- 티켓 도메인 — 상태 기계, 수명주기, 해결 판정
- 승격 워크플로우 — 티켓 해결 → 지식 항목, 반복 질문 → FAQ
- 운영자 대시보드 — 작업 대기열 여덟 종과 현황 화면 네 종, 대기열 우선순위와 알림
- 통계·지표 정의와 품질 회귀 감지
- 모 시스템 연동 계약과 어댑터 격리 (소스 리더 · QnA 리더 · 게재 라이터)
- 논리 아키텍처 — 컴포넌트 경계, 지식(파일)/운영(DB) 저장소 분리, 온라인/배치 실행 경로 분리
- QnA 기록의 개인정보 취급 정책

### 제외 영역

- 최종 이용자 대면 UI — 모 시스템이 렌더링한다
- 최종 이용자의 계정·인증·권한 관리 — 모 시스템의 책임이다
- 모 시스템의 도메인 데이터와 비즈니스 로직
- 모 시스템 소스코드에 대한 쓰기 — 읽고 추적할 뿐, 고치거나 PR 을 내지 않는다
- 모 시스템에 대한 그 밖의 쓰기 조치 — 허용된 쓰기는 **QnA 답변 게재 하나뿐**이다
- 외부 ITSM 도구 (Jira SM / Zendesk / ServiceNow) 연동 — 티켓은 이 시스템이 직접 소유한다
- LLM 모델 자체의 fine-tuning / 학습 파이프라인
- 외부 reference (llm-wiki / OKF) 의 코드 직접 차용 — 컨셉만 흡수하고 형식은 우리 spec 으로 재정의한다
- 인프라 IaC (Terraform / CDK) 자동화

## 4. Evolving Thesis

*현재까지의 working hypothesis* (시간에 따라 변한다):

- 이 시스템의 본체는 QnA 응답이 아니라 **지식베이스**다. 응답·FAQ·통계는 그 위에서 나오는 표현이다
- 지식 원천이 **둘**(소스코드 · QnA)이고 성격이 다르다는 것이 이 구조의 힘이다 — 소스는 *실행되는 진실*, QnA 는 *관찰된 현상*이며, 둘이 서로를 검증한다
- **출처(provenance)는 메타데이터가 아니라 1급 시민**이다. 출처가 없으면 stale 판정도 교차 검증도 근거 부착도 성립하지 않는다
- 소스코드 원천이 있으므로 **stale 판정이 시간이 아니라 커밋 기준**으로 정확해진다 — 이것이 일반 위키 대비 우위다
- 모순은 한쪽을 지워 해소하지 않는다. **양쪽을 남기고 표시**하고, 판단은 사람이 한다
- 로컬 LLM 선택은 성능 타협이 아니라 **소스코드를 외부로 내보내지 않기 위한 제약**이며, 그 제약이 배치·반복 ingest 를 비용 없이 가능하게 한다
- llm-wiki 는 *운영 모델*, OKF 는 *교환 형식* 으로 층이 다르다. 겹치지 않게 나눠 쓴다
- **게재는 되돌리기 어려운 대외 행위**다. 자동 게재는 검토자를 루프에서 빼는 대가로 속도를 얻는 거래이며, 그 거래 조건이 게재 판정 기준이다
- **자기 ingest 되먹임은 구조적 함정**이며, 그 차단은 **봇 계정이라는 기계적으로 확정 가능한 사실**로 한다 — 내용 판별이나 신뢰도 점수 같은 흐릿한 기준을 쓰지 않는다
- 다만 **해결 확정은 외부 검증 신호**다. 답이 실제로 문제를 풀었다면 그것은 더 이상 검증되지 않은 자기 산출물이 아니므로, 배제를 유지할 이유가 없다
- 그래서 **되먹임 차단의 강도는 해결 판정의 강도와 같다**. 무응답을 해결로 세는 순간 차단은 이름만 남는다 — 그래서 해결은 **명시적 / 암묵적 두 등급**이다
- 암묵적 해결은 버려지는 것이 아니라 **대기하는 것**이다. 사람이 확인해 주면 명시적으로 상향되고 그때 지식이 된다 — 운영자의 확인 행위 자체가 지식베이스를 키우는 작업이 된다
- **해결률을 하나의 숫자로 뭉치면 품질이 가려진다.** 명시적 해결률이 진짜 품질 지표이고, 암묵적 해결 비율은 단독으로 읽을 수 없는 경고 지표다
- **답변과 콘텐츠는 트리거만 다른 같은 것**이다 — 하나는 질문에 반응하고 하나는 주기에 반응할 뿐, 지식베이스에서 나와 검수를 거쳐 나간다는 점은 같다. 그래서 파이프라인은 하나면 된다
- 콘텐츠 확장은 **구현이 아니라 선언**이어야 한다. 타입마다 별도 구현이 쌓이면 유지가 불가능해진다
- **살아있는 문서와 발행물은 다른 물건이다** — 전자는 갱신으로 stale 을 흡수하지만, 후자는 회수할 수 없다. 그래서 발행물의 검수는 더 엄격해야 한다
- **지식을 파일에 두는 것은 취향이 아니라 llm-wiki·OKF 차용의 논리적 귀결이다** — 1 커밋 = 1 ingest, additive merge, 번들 형식은 모두 파일 트리를 전제한다. DB 행으로 넣으면 차용한 운영 모델이 성립하지 않는다
- 반대로 QnA 상태·티켓·통계는 조건 질의와 집계가 필요하므로 DB 다. **두 저장소를 잇는 것은 출처(provenance)** 이며, 그 링크가 stale 전파와 정정 추적의 경로가 된다
- **규칙은 한 곳에서만 집행한다.** 되먹임 차단이 여러 곳에 흩어지면 언젠가 한 곳이 새고, 새는 순간 오답이 지식으로 굳는다 — 지식베이스는 틀린 채로도 잘 동작하는 것처럼 보이므로 사후 발견이 어렵다
- **운영자는 감시자가 아니라 루프의 일부다.** 암묵적 해결 확인·승격 승인·모순 판정이 멈추면 루프는 느려지는 것이 아니라 끊긴다 — 이 시스템의 처리량 상한은 로컬 LLM 속도가 아니라 **운영자가 대기열을 소화하는 속도**일 가능성이 높다
- **사고를 내는 대기열과 조용히 정체시키는 대기열은 다르다.** 후자(암묵적 해결 확인·승격·지식 공백)는 방치해도 아무 일이 없어서 영원히 밀리고, 그 결과 시스템은 사고 없이 성장을 멈춘다
- 검수 반려율·승격 거부율은 품질 지표인 동시에 **운영자가 에이전트를 신뢰하는지의 계측기**다
- 칼럼은 이 시스템의 원칙과 **구조적으로 불편하다** — 지식베이스는 사실을 주지 의견을 주지 않는데 칼럼은 해석을 요구한다. 선을 긋지 않으면 근거 원칙이 여기서 새어 나간다
- 지식으로 삼지 않는 것과 기록하지 않는 것은 다르다. 봇 답변을 통째로 없는 셈 치면 통계와 FAQ 가 함께 죽는다
- **게재는 끝이 아니라 과정이다** — QnA 항목은 해결까지 추적되는 상태 엔터티이고, 답변 파이프라인은 항목당 1회가 아니라 후속마다 재실행된다
- 미해결로 종료된 QnA 는 버릴 데이터가 아니라 **지식 공백의 좌표**다. 지식베이스가 못 답하는 영역을 가리킨다
- 지식이 자라는 것과 오답이 자라는 것은 **같은 메커니즘**을 쓴다. 루프를 세게 돌릴수록 검문이 중요해진다
- 승격(promotion)이 루프를 닫는 유일한 연결 고리이므로, 승격 정책의 설계가 곧 시스템 품질의 상한이다
- 실서비스에서는 "모른다 + 티켓"이 근거 없는 답변보다 낫다. 침묵은 실패가 아니라 설계된 경로다
