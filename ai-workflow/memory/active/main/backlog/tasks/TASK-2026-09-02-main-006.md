## 🛠️ Implementation / Content

- Progress: 기록된 위험은 인증과 CSRF **둘**을 함께 말한다. 인증만 넣고 브라우저가 자동으로 자격을 실어 보내는 방식(HTTP Basic)을 쓰면 CSRF 는 그대로 남는다 — 그래서 `SameSite=Strict` 세션 쿠키로 간다. 다른 사이트의 form POST 는 쿠키를 싣지 못하므로 한 장치가 둘을 덮는다.
- Progress: **암호는 쿠키에 실리지 않고, 별도 비밀키도 두지 않는다.** 쿠키에 싣는 것은 `발급시각.HMAC(암호, 발급시각)` 이라 훔쳐도 암호가 나오지 않고, **발급 시각이 서명 안에 있어 만료를 뒤로 미룰 수 없다.** 서명 열쇠를 암호 자체로 삼은 이유는 별도 비밀키를 어디 둘지가 새 문제가 되기 때문이고(파일이면 백업에 섞이고 설정이면 값이 둘이 된다), 부수 효과가 오히려 바람직하다 — **암호를 바꾸면 살아 있는 세션이 전부 죽는다.**
- Progress: **강제하는 자리를 앱이 아니라 기동에 뒀다.** 앱은 암호가 선언됐을 때만 인증하고, **선언하지 않은 채 밖에 여는 것**은 `check_live_exposure` 가 막는다(WBS-5.2.1 의 조건 (2)가 이제 `web_password` 를 보고 풀린다). 루프백 개발 구성에 암호를 강제하면 시험과 로컬 실행이 전부 그것을 들고 다녀야 하고, 그 부담은 결국 암호를 코드에 적게 만든다.
- Progress: **GET 은 로그인으로 보내고 나머지는 401 로 끊는다.** 판정 요청(POST)을 로그인 화면으로 리다이렉트하면 브라우저가 그것을 성공으로 읽어 **누른 사람은 처리된 줄 안다.** `/health` 는 열어 뒀다 — 기동 확인이 암호를 들고 다니게 하지 않는다.
- Progress: **`secure` 쿠키는 켜지 않았다.** 이 화면은 사내망·tailnet 위 평문 http 가 전제라(§8) 켜면 그 구성에서 쿠키가 저장되지 않아 **인증을 켠 순간 로그인할 수 없게 된다.**
- Progress: **라이브 확인 (포트 8899, 인증 켬).** `/health` 200 · `GET /` → 303 `/login?next=/` · 판정 POST → 401 · 틀린 암호 → 401 · 맞는 암호 → 303 + `SameSite=strict; HttpOnly` 쿠키 발급, 그 쿠키로 화면 200.
