# ADR-001 — 구현 스택과 프로세스 구조

- 상태: accepted
- 결정일: 2026-08-28
- 해소: CO-8 (기술 선택)
- 관련: [ADR-005](./ADR-005-llm-runtime.md), [ADR-007](./ADR-007-dashboard.md)

## 맥락

운영은 **1인 겸업**(CO-7)이고, 실행 경로는 온라인과 배치로 나뉘어야 하며(NFR-6),
대시보드는 웹 UI 를 새로 만든다.

1인 겸업이라는 조건이 스택 선택의 대부분을 결정한다 — **운영 부담이 곧 처리량 상한**이다(§8.4).

## 결정

**Python 단일 언어로 만든다. 프론트엔드도 별도 언어를 쓰지 않는다.**

| 층 | 선택 | 이유 |
|---|---|---|
| 백엔드 | **Python** | LLM · 문서 처리 생태계. pi 하네스와 결이 같다 |
| 웹 UI | **서버 렌더링 + 최소 JS** | 대시보드는 목록·상세·버튼이 대부분이다. SPA 가 필요한 상호작용이 없다 |
| 프로세스 | **온라인 1 + 배치 1**, 같은 코드베이스 | NFR-6. 코드는 공유하고 실행만 나눈다 |

### 왜 SPA 를 만들지 않는가

대시보드가 하는 일은 **대기열을 보여주고 승인·반려 버튼을 누르는 것**이다(§6.4.4).
지식 편집기도 만들지 않는다(D39). 이 상호작용에는 클라이언트 상태가 거의 없다.

SPA 를 택하면 언어가 둘이 되고, 빌드 파이프라인이 생기고, 1인이 두 스택을 유지해야
한다. **얻는 것에 비해 유지비가 크다.**

## 대안과 기각 이유

| 대안 | 기각 이유 |
|---|---|
| TypeScript 단일 | 로컬 LLM 런타임·문서 처리 생태계가 얇다. ingest 파이프라인이 이 시스템의 본체(D1)이므로 그쪽 생태계를 따른다 |
| 백엔드 Python + 프론트 TS | 1인 겸업에게 스택이 둘이 된다. 대시보드의 상호작용이 그 값을 하지 않는다 |
| 모 시스템과 같은 스택 | 모 시스템이 다언어 혼재(§1.1)라 "같은 스택"이 정의되지 않는다 |
| 온라인·배치를 한 프로세스에 | 배치 ingest 가 웹 응답을 막는다. NFR-6 위반 |

## 귀결

- **좋은 것**: 유지할 스택이 하나. 배포 단위가 단순하다
- **나쁜 것**: 프론트 상호작용을 크게 늘리려면 이 결정을 되돌려야 한다.
  다만 §8.5.5 가 대시보드를 "지목하는 곳"으로 한정했으므로 그럴 일이 적다
- **되돌리는 비용**: 중간. 서버 렌더링 화면을 API + SPA 로 바꾸는 작업이다

## 남는 것

구체적 웹 프레임워크와 템플릿 엔진은 구현 시 정한다 — 이 ADR 이 정하는 것은
**언어를 하나로 두고 서버 렌더링으로 간다**는 방향이다.
