# ADR-010 — 스키마는 번호 매긴 계단으로 올리고, 사람이 명령으로 돌린다

- 상태: accepted
- 결정일: 2026-08-28
- 관련: [ADR-002](./ADR-002-storage.md), [ADR-005](./ADR-005-llm-runtime.md)

## 맥락

운영 DB 는 SQLite 파일 하나다(ADR-002). 지금까지 스키마는 `CREATE TABLE IF NOT EXISTS`
한 벌이었고, 연결을 열 때마다 그것을 통째로 다시 실행했다.

**그 방식은 표는 만들지만 열은 만들지 않는다.** 옛 DB 로 새 코드를 돌리면
`table ticket has no column named state_at` 로 터진다 — 재현해 확인했다. 조용히
틀리지는 않고 크게 실패하지만, **터지는 자리가 배치 한복판**이라 그때까지 처리한
것과 못 한 것이 섞인다.

개발 중에는 파일을 지우면 됐다. S3(WBS-4.5) 에서만 세 표가 바뀌었고 그때마다 그렇게
했다. 그런데 **4.5 를 실데이터로 켜는 순간 그 방법이 사라진다.**

한 가지가 이 결정의 조건을 좁힌다. **온라인(`asd-web`)과 배치(`asd-worker`)는 다른
프로세스**이며 같은 파일을 연다(ADR-002).

## 결정 1 — 번호 매긴 계단  {#numbered}

> `schema_version` 에 적용 이력이 쌓이고, 각 이행은 **번호와 이름을 가진 문장 목록**이다.

대안이었던 *선언적 대조 + 자동 `ADD COLUMN`*(현재 스키마를 SSOT 로 두고 없는 열만
자동으로 더하기)은 두 벌이 어긋날 자리가 없다는 점이 매력이지만, **데이터 채우기와
제약 변경을 표현할 수 없다.** 그런 이행은 반드시 오고, 그때는 결국 손으로 SQL 을
짜게 된다 — 두 방식이 공존하면 **어느 변경이 자동이고 어느 것이 아닌지 아무도
기억하지 못한다.**

문장 목록이지 함수가 아닌 것도 의도다. 이행은 **읽고 승인하는 것**이 사람의 일이므로,
무엇이 실행되는지 알려고 코드를 따라가야 해서는 안 된다.

## 결정 2 — 사람이 명령으로 올린다  {#explicit}

> `asd migrate` 가 유일한 이행 경로다. 자동 적용하지 않는다.

이유는 셋이다.

| 이유 | 설명 |
|---|---|
| **경쟁** | 온라인·배치가 동시에 뜨면 둘 다 올리려 한다. 파일 락으로 막을 수는 있으나, 막아야 할 상황을 애초에 만들지 않는 편이 낫다 |
| **되돌리기 어려움** | 이행은 게재와 같은 종류의 대외 행위다(§5.2 의 성격). **조용히 일어나면 안 된다** |
| **비용이 낮다** | 운영자가 곧 개발자다(D30). 배포 때 명령 하나를 더 치는 부담이 작다 |

## 결정 3 — 버전이 안 맞으면 기동을 거부한다  {#refuse}

> 두 프로세스 모두 기동 시 버전을 대조하고, 맞지 않으면 **아무것도 시작하지 않는다.**

지금도 결국 터지지만 터지는 자리가 배치 한복판이다. 기동에서 드러내면 **아무 일도
시작되지 않은 상태**에서 알게 된다 — 설정 누락을 기동에서 드러내기로 한 것과 같은
이유이며, 그 판단은 실제로 한 번 값을 했다.

확인은 `operations/preflight.py` 한 곳에 둔다. 프로세스마다 따로 두면 한쪽만
고쳐지고, 그러면 **거부되지 않는 프로세스가 옛 스키마 위에서 돈다.**

내려가는 계단은 두지 않는다. 롤백은 되돌릴 수 없는 데이터 변형을 포함할 수 있어
기계가 판단할 일이 아니다. DB 가 코드보다 앞서면 그 사실을 말하고 멈춘다.

## 결정 4 — 선언과 계단의 어긋남을 대조로 갚는다  {#verify}

`SCHEMA_SQL`(현재 스키마의 선언)과 마이그레이션(기존 DB 를 거기 맞추는 계단)은
**두 벌이다.** 어긋나면 새로 설치한 환경과 이행한 환경의 스키마가 달라지는데, 그
차이는 한참 뒤 엉뚱한 곳에서 드러난다.

> `asd migrate` 는 적용 뒤 **결과 스키마를 선언과 대조**한다. 다르면 통째로 롤백하고
> 무엇이 다른지 말한다.

선언을 버리고 마이그레이션만 남기는 대안도 있었다(새 DB = 계단 전부 적용). 그러면 두
벌이 아예 없어지지만, `SCHEMA_SQL` 은 이 저장소에서 **읽는 문서** 역할이 크다 — 각
열이 어느 결정을 떠받치는지가 거기 주석으로 있고, 그것을 계단 파편으로 흩으면
스키마를 한자리에서 읽을 수 없게 된다.

규칙을 두 벌 쓰는 대가를 대조 시험으로 갚는 것은 이 저장소가 **산출물 필터**에서
이미 한 방식이다(`judge()` 와 SQL). 여기서는 시험이 아니라 **실행 시점에** 대조한다 —
실제 데이터 위에서 확인하는 편이 더 강하기 때문이다.

## 결정 5 — 버전을 모르는 DB 는 받지 않는다  {#unknown}

`schema_version` 이 없는데 표는 있는 DB 는 **버전을 알 수 없다.** 짐작해 번호를
찍으면 그 뒤의 모든 이행이 어긋나므로 거부한다.

> `None`(모른다)과 `0`(아무것도 적용되지 않았다)을 **섞지 않는다.** 섞으면 이행 경로
> 이전의 DB 에 계단을 처음부터 놓으려 하고, 이미 있는 표를 다시 만들다 터지거나
> 더 나쁘게는 절반만 적용된다.

지금은 개발 단계라 그런 DB 는 지우면 된다. **이 한 번의 단절을 감수하는 것이 이
결정을 지금 내리는 이유**다 — 나중에는 감수할 수 없다.

## 귀결

- `initialize()` 는 **새 DB 일 때만** 전체 스키마를 적용하고 버전을 찍는다.
  기존 DB 에는 손대지 않는다 — 예전처럼 매번 `executescript` 를 돌리면 **표 추가는
  조용히 되고 열 추가만 실패해** 이행이 반쪽이 된다.
- 스키마를 바꾸는 길은 이제 `asd migrate` 하나다. 표 추가도 마이그레이션이 필요하다.
- **baseline 은 v1**, 곧 S3 까지의 스키마다. 다음 스키마 변경부터 계단이 쌓인다.

## 대안과 기각 이유

| 대안 | 기각 이유 |
|---|---|
| 선언적 대조 + 자동 `ADD COLUMN` | 데이터 채우기·제약 변경을 표현할 수 없다. 결국 손 SQL 과 공존하게 되고, 어느 쪽이 자동인지 흐려진다 |
| 번호 계단 + 기동 시 자동 적용 | 두 프로세스가 경쟁한다. 코드를 되돌려도 DB 는 앞서 있고, 무엇이 언제 바뀌었는지 로그를 뒤져야 안다 |
| Alembic | 1인 운영에 의존성과 개념(리비전 그래프·브랜치)이 는다. 계단이 선형이고 수가 적어 정당화되지 않는다 |
| 선언을 버리고 계단만 남기기 | `SCHEMA_SQL` 의 설계 주석이 파편으로 흩어져 스키마를 한자리에서 읽을 수 없게 된다 |
| 내려가는 계단(down migration) | 되돌릴 수 없는 데이터 변형을 포함할 수 있다. 기계가 판단할 일이 아니다 |
