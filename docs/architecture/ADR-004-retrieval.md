# ADR-004 — 검색 방식

- 상태: accepted
- 결정일: 2026-08-28
- 해소: O31
- 관련: [ADR-003](./ADR-003-knowledge-granularity.md), [ADR-005](./ADR-005-llm-runtime.md)

## 맥락

파이프라인 2단계(지식베이스 조회)가 근거를 찾지 못하면 답변이 만들어지지 않고
티켓으로 간다(FR-18). **검색 품질이 곧 커버리지**다.

두 가지 조건이 설계를 좌우한다.

| 조건 | 함의 |
|---|---|
| 항목 수가 **수백~수천**(ADR-003) | 전수 임베딩이 부담되지 않는다 |
| **어휘 격차**(§2.5.4) — 이용자는 "결재", 코드는 `approval` | 키워드만으로는 못 찾는다 |

## 결정

**하이브리드로 간다 — 키워드 + 임베딩, 그리고 LLM 재랭킹.**

| 단계 | 하는 일 |
|---|---|
| 1 | **키워드 검색** — 정확한 식별자·에러 메시지에 강하다 |
| 2 | **임베딩 검색** — 표현이 다른 같은 개념을 잡는다. 로컬 GPU 로 수행(ADR-005) |
| 3 | 두 결과를 합쳐 **LLM 이 재랭킹**하고 근거 후보를 고른다 |

규모가 작아 **전체를 임베딩해도 비용이 미미하다.** 인덱스 재생성도 ingest 주기에
맞춰 통째로 다시 해도 된다 — 증분 인덱싱의 복잡도를 지금 떠안지 않는다.

### 사용자 표현 사전을 별도 인덱스로 둔다  {#vocab-index}

§2.5.4 는 **어휘 격차를 메우는 것이 QnA 원천의 고유 기여**라고 했다. 그것을 실제
장치로 만든다.

> QnA 이력에서 **표현 → 개념** 매핑을 추출해 별도 인덱스로 유지한다.
> "결재 반려"라고 물으면 이 인덱스가 `approval` 관련 지식 항목을 가리킨다.

이 인덱스는 **QnA 가 쌓일수록 좋아진다** — 두 원천 구조가 검색에서 값을 하는 지점이다.
1국면에는 비어 있고, 그래서 1국면의 커버리지가 낮은 것이 정상이다(§1.3).

### 구현하며 드러난 것 — 임베딩은 표준이 없다  {#no-embedding-standard}

채팅은 OpenAI 호환이 사실상 표준이 됐지만 **임베딩은 그렇지 않다.** 2026-08-28
조사에서 MiniMax 가 그 예임을 확인했다.

| | OpenAI 형식 | MiniMax `embo-01` |
|---|---|---|
| 요청 본문 | `input` | **`texts`** |
| 색인/질의 구분 | 없다 | **`type`: `db` \| `query` — 필수** |
| 응답 | `data[].embedding` | **최상위 `vectors`** |
| 오류 | HTTP 상태 | **`base_resp.status_code`** (0 이 성공) |

마지막이 특히 위험하다 — **HTTP 200 을 받고도 실패**일 수 있어 `raise_for_status()`
만으로는 놓친다.

> 그래서 임베딩 제공자를 **채팅과 분리**했다. ADR-005 결정 4("모델을 교체 가능하게
> 감싼다")가 예상한 경우가 바로 이것이다.

#### 라이브 검증 결과 (2026-08-28)  {#live-verified}

실제 키로 호출해 **문서상의 형태가 맞음을 확인**했다.

| 확인한 것 | 결과 |
|---|---|
| `texts` 가 필수인가 | **그렇다.** `input` 만 보내면 `2013 invalid params, expr_path=texts, cause=missing required parameter` |
| 응답 최상위가 `vectors` 인가 | **그렇다** |
| 실패가 HTTP 200 으로 오는가 | **그렇다.** 레이트 리밋이 `HTTP 200` + `base_resp.status_code=1002` 로 왔다 |
| 성공 시 벡터 차원 | **확인 못 했다** — 이 키로는 임베딩이 계속 레이트 리밋이었다 |

세 번째가 이 어댑터를 따로 만든 이유를 그대로 보여준다. `raise_for_status()` 만 썼다면
**`vectors: null` 을 정상 응답으로 받아** 다음 단계에서 엉뚱한 오류로 터졌을 것이다.

> **임베딩이 이 키로는 쓰이지 않는다.** 2분간 6회 재시도가 모두 RPM 제한이었다.
> 개발 환경의 임베딩 경로는 다른 방법이 필요하다 — **O57** 로 남긴다. 검색은
> WBS-4.4.1 이므로 지금 막히지는 않는다.

#### `type` 요구는 잡음이 아니다  {#purpose-is-real}

MiniMax 가 요구하는 `db` / `query` 구분은 **우리 설계에 이미 있던 것**이다 —
지식 항목을 *색인*하는 것과 질문으로 *질의*하는 것은 다른 일이다.

OpenAI 형식이 그 구분을 노출하지 않을 뿐이므로, **인터페이스에는 둔다**
(`EmbeddingPurpose`). 형식이 무시하더라도 나중에 넣으려면 호출부를 전부 고쳐야 한다.

## 대안과 기각 이유

| 대안 | 기각 이유 |
|---|---|
| 키워드만 | 어휘 격차를 못 넘는다. 사내 시스템 질문의 상당수가 여기 걸린다 |
| 임베딩만 | 정확한 식별자·에러 코드 검색이 약해진다. 개발자가 코드 용어로 물을 때 놓친다 |
| 외부 벡터 DB | 규모가 작아 과잉이다. 운영 부담(CO-7)만 는다 |
| 외부 임베딩 API | **NFR-1 위반** — 지식 항목 내용이 소스코드에서 파생되므로 반출이다 |

## 귀결

- 인덱스가 **셋**(키워드 · 임베딩 · 표현 사전)이 되어 재생성 대상이 는다
- LLM 재랭킹이 붙어 **조회 지연이 늘어난다.** 질문량이 적어(§1.3.1) 감당 가능하지만,
  폴링 주기(NFR-7)와 합쳐 답변 지연에 더해진다는 점은 §8.6.3 이 이미 경고했다
- 표현 사전이 비어 있는 1국면에는 커버리지가 낮다 — **고장이 아니라 정상**(D14)
